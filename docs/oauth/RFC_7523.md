# RFC 7523 — JSON Web Token (JWT) Profile for OAuth 2.0 Client Authentication and Authorization Grants

> **Status:** Standards Track
> **Published:** 2015-05
> **L-tier / T-tier:** L4 (jwt-bearer grant) + L5 (private_key_jwt / client_secret_jwt client auth) · T5
> **OneAuth coverage:** Grant: Implemented. Client auth: Implemented (`client_secret_jwt` PR 293; `private_key_jwt` shipped)
> **See also:** [`RFC_7521.md`](RFC_7521.md) · [`RFC_8693.md`](RFC_8693.md) · [`LANDSCAPE.md`](LANDSCAPE.md)

## In one sentence

RFC 7523 is the JWT-specific binding of the [7521 assertion framework](RFC_7521.md) —
it lets a signed JWT serve as either (a) the grant that authorizes a token
mint, or (b) the client's credentials at `/token`. Same wire shape, two
purposes.

## What problem does it solve?

| Without 7523 | With 7523 |
|---|---|
| `client_secret_basic` leaks a shared secret on every request; `client_secret_post` is no better | Asymmetric (private_key_jwt) or HMAC-keyed (client_secret_jwt) signed assertion — proof of possession, no secret on wire |
| Service-to-service trust requires shared credentials in every direction | One service signs a JWT with its private key; the other verifies via JWKS — no shared state |
| Cross-org federation needs custom token-exchange protocols | "Here's a JWT signed by my issuer" is the universal handoff |

7523 is two specs in one document, and the dual-use is on purpose. The
*client authentication* mode replaces leaky shared secrets; the *grant*
mode enables federated delegation.

## Relatable example

**Mode A — client authentication (private_key_jwt).** Your backend service
authenticates to a partner API:

- At setup time, your service registers a public key with the partner AS.
- For every `/token` call, your service constructs and signs a fresh JWT:
  `{iss: "your-client-id", sub: "your-client-id", aud: "https://partner/token", exp: now+60, jti: uuid}`,
  signed with your private key.
- POSTs it as `client_assertion`. Partner verifies via your published
  public key.

No shared secret. Stolen-secret class of attacks eliminated. This is what
private_key_jwt does.

**Mode B — JWT-bearer grant.** GitHub Actions deploys to AWS:

- GitHub issues a signed OIDC token to the CI job:
  `{iss: "https://token.actions.githubusercontent.com", sub: "repo:org/repo:ref:main", aud: "sts.amazonaws.com", ...}`.
- The CI job presents this JWT as `assertion=<jwt>` with
  `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` to AWS.
- AWS validates against GitHub's JWKS, applies its trust policy, returns
  AWS-format credentials.

(In practice AWS uses its own STS API shape that predates RFC 7523, but the
semantic is exactly the grant mode of 7523.)

## Key concepts

1. **Two modes, one spec**:
   - **Grant mode (§2.1)**:
     `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`,
     `assertion=<JWT>`. The JWT is the *authorization*.
   - **Client auth mode (§2.2)**:
     `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`,
     `client_assertion=<JWT>`. The JWT is the *client credential*.
2. **Required JWT claims**: `iss`, `sub`, `aud`, `exp`. For client auth,
   `iss == sub == client_id`; for grant mode, `iss` is the trusted issuer
   and `sub` is the subject identity being delegated.
3. **`aud` must include the AS's token endpoint URL.** Prevents
   cross-AS replay.
4. **Short-lived; `jti` for one-time use.** RFC 7523 recommends "as short
   as possible" lifetimes — typically 30–300 seconds. `jti` enables the AS
   to detect replay.
5. **Symmetric vs asymmetric**: 7523 covers both — `private_key_jwt`
   (RSA/ECDSA, public key published; preferred) and `client_secret_jwt`
   (HMAC-SHA256, key is the client_secret).

## Wire example

**Client authentication via private_key_jwt:**

```http
POST /api/token HTTP/1.1
Host: as.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&scope=read
&client_id=my-service-account
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=eyJhbGciOiJSUzI1NiIsImtpZCI6Im15LWtleS0xIn0.eyJpc3MiOiJteS1zZXJ2aWNlLWFjY291bnQiLCJzdWIiOiJteS1zZXJ2aWNlLWFjY291bnQiLCJhdWQiOiJodHRwczovL2FzLmV4YW1wbGUuY29tL2FwaS90b2tlbiIsImV4cCI6MTcxNzAwMDA2MCwiaWF0IjoxNzE3MDAwMDAwLCJqdGkiOiJjbGllbnQtYXNzZXJ0aW9uLWFiYzEifQ.signature_bytes
```

Decoded `client_assertion`:

```json
{ "iss":"my-service-account", "sub":"my-service-account",
  "aud":"https://as.example.com/api/token",
  "exp":1717000060, "iat":1717000000, "jti":"client-assertion-abc1" }
```

AS validates: signature against published JWK for `my-service-account`,
`iss == sub == client_id`, `aud` matches token endpoint, `exp` future,
`jti` not seen before.

**JWT-bearer grant:**

```http
POST /api/token HTTP/1.1
Host: as.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion=<github-issued-OIDC-token>
&scope=deploy
```

AS validates the OIDC token (via the trusted issuer's JWKS), applies its
policy ("does sub=repo:org/repo allow scope=deploy?"), mints an access
token.

## Where it lands on the OAuth abstraction

- **L4 grant + L5 client auth.** Same RFC fills two slots.
- **T5 (token endpoint).** Both modes act at `/token`.
- 7523 is the concrete binding of [RFC 7521](RFC_7521.md)'s framework.

## OAuth 2.0 status

Part of the 2.0 ecosystem from 2015. The dominant non-shared-secret client
authentication today. JWT-bearer grant is the basis for nearly every
modern federation flow.

## OAuth 2.1 status

Not changed by 2.1. The two modes carry through unchanged.

## Migration path (shared-secret → assertion-based client auth)

Most production deployments still use `client_secret_basic` for confidential
clients. Migration to `private_key_jwt`:

1. **Generate an asymmetric key pair** per client. Publish the public key
   in the client's `jwks` (or `jwks_uri`) metadata via DCR (RFC 7591).
2. **Client constructs a fresh `client_assertion` JWT per token call.**
   Library support is universal (golang-jwt, jose-jwt, jsonwebtoken).
3. **AS validates** — OneAuth does this via
   `ClientAuthenticator.AuthenticateClient` (`apiauth/client_authenticator.go:102`).
4. **Remove the `client_secret`** from the client's registration once all
   token calls use private_key_jwt. Defense-in-depth — without a secret to
   leak, there's no secret-leak attack.

The asymmetric variant (`private_key_jwt`) is the long-term recommendation.
The symmetric (`client_secret_jwt`) is a transition path for deployments
that can't yet manage asymmetric keys per client.

The `client_secret_jwt` + `private_key_jwt` pair gives OneAuth one of the
strongest L5 client auth postures in the OAuth library landscape, well
ahead of bare-secret deployments.

### ID-JAG redemption hardening (MCP Enterprise-Managed Authorization)

When the presented assertion is an ID-JAG (JWS `typ == oauth-id-jag+jwt`),
the jwt-bearer grant applies EMA-specific hardening on top of plain §2.1:

- **Single-use.** The ID-JAG `jti` is recorded in a `JTIStore` (the same
  replay interface used for client-assertion defense); a replayed ID-JAG is
  rejected with `invalid_grant`. In-memory by default; swap in a distributed
  store via `JwtBearerGranterConfig.ReplayStore` / `OneAuthConfig.IDJAGReplayStore`.
- **Audience binding.** The ID-JAG `aud` (the resource app's AS) is checked
  against this AS via the standard §3 audience validation.
- **client_id binding.** The issued MCP access token carries the ID-JAG's
  `client_id` claim (draft §5), so the resource server sees which client the
  IdP vouched for.

Plain jwt-bearer assertions (no ID-JAG `typ`) are unaffected. Issuance is the
sibling [RFC 8693](RFC_8693.md) token-exchange path. `act`/actor propagation
for agent-vs-user identity is a tracked follow-up (mcpkit ext-auth#13).

## When NOT to use it

- **Tiny prototypes / dev** — `client_secret_basic` is operationally
  simpler. Don't over-engineer.
- **Strictly internal deployments with controlled networks** — the
  marginal security benefit may not justify the JWT-construction overhead.
- **Public clients (no secret)** — assertion auth doesn't apply; use
  PKCE instead.

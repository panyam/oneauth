# RFC 9396 — OAuth 2.0 Rich Authorization Requests (RAR)

> **Status:** Standards Track
> **Published:** 2023-05
> **L-tier / T-tier:** L6 · T1 (prepare) + T5 (carry through mint) + T7 (verify at RS)
> **OneAuth coverage:** Implemented (`core/authorization_details.go` + `apiauth/` token / introspection / middleware)
> **See also:** [`RFC_9126.md`](RFC_9126.md) · [`RFC_9101.md`](RFC_9101.md) · [`LANDSCAPE.md`](LANDSCAPE.md)

## In one sentence

RAR replaces the flat `scope` string with a structured
`authorization_details` JSON array — letting the request express *exactly*
what's being asked for (e.g., "transfer £500 from account A to merchant B
once") rather than a coarse "payments" scope.

## What problem does it solve?

| Without RAR | With RAR |
|---|---|
| `scope="payments"` means "all payment operations forever" — coarse, dangerous | `authorization_details=[{type:"payment", amount:500, beneficiary:"B"}]` is precise and one-shot |
| Banking, healthcare, and regulated APIs invent ad-hoc parameters to carry transaction-specific details | One spec; one place to put structured authorization data |
| Audit trails (what was authorized?) need to parse out vendor-specific extensions | `authorization_details` is the canonical record |
| Step-up authentication (mid-session, "approve this particular transfer") needs request-specific data | RAR is the natural carrier — `type` + per-type schemas |

RAR is the *expressivity* upgrade for authorization. Scope is "what API
surface"; RAR is "what specific operation, with what parameters." They're
complementary — most deployments ship both.

## Relatable example

UK Open Banking payment initiation under PSD2 — the canonical RAR use case
that drove the spec:

A third-party payment service provider (PSP) wants to initiate a £500
transfer from a customer's account at HSBC to merchant ACME. Without RAR,
the authorization is "the PSP can do payment operations" — vague,
dangerous, hard to audit. With RAR, the authorization request says
*exactly* what's being asked:

```json
"authorization_details": [{
  "type": "payment_initiation",
  "actions": ["initiate"],
  "instructedAmount": {
    "currency": "GBP",
    "amount":   "500.00"
  },
  "creditorName": "ACME Corp",
  "creditorAccount": {
    "iban": "DE89370400440532013000"
  }
}]
```

The customer's bank shows them the actual transaction details on the
consent screen. The customer approves the *specific transfer*, not the
PSP's general access. The issued access token carries the same
`authorization_details` — the RS verifies the operation matches.

Any future API call from the PSP that tries to do something different (a
different amount, a different beneficiary) is rejected because the token's
`authorization_details` don't match.

## Key concepts

1. **`authorization_details` is an array of objects.** Each object has
   at minimum a `type` field naming a *type-specific schema*. Beyond
   `type`, the schema is defined per type — by the AS, an industry
   profile, or a regulator.
2. **Three places the data appears on the wire**:
   - In the authorization request (T1): `authorization_details` URL/POST param
   - In the token response (T5): mirrored back so the client knows what was granted
   - In the token claims / introspection response (T7): the RS reads it
3. **Composes with `scope`.** Not exclusive — many deployments use scope
   for coarse-grained capabilities and RAR for transaction details.
   `scope=payments authorization_details=[{type:"payment_initiation", ...}]`.
4. **`type` values are registered.** OpenID has defined `payment_initiation`,
   `account_information`, `customer_information`, etc. Industry profiles
   (Open Banking, healthcare) add more. AS can advertise the types it
   accepts via `authorization_details_types_supported` (RFC 8414).
5. **Cross-spec composition.** RAR rides naturally inside PAR (RFC 9126)
   and JAR (RFC 9101). The combination — structured authorization
   (RAR), back-channel transport (PAR), signed integrity (JAR) — is the
   FAPI 2.0 baseline.

## Wire example

**Authorization request with RAR:**

```http
GET /authorize?response_type=code
              &client_id=psp-1
              &redirect_uri=https%3A%2F%2Fpsp.example%2Fcb
              &scope=openid
              &state=xyz
              &code_challenge=E9Mel...
              &code_challenge_method=S256
              &authorization_details=%5B%7B%22type%22%3A%22payment_initiation%22%2C%22actions%22%3A%5B%22initiate%22%5D%2C%22instructedAmount%22%3A%7B%22currency%22%3A%22GBP%22%2C%22amount%22%3A%22500.00%22%7D%2C%22creditorName%22%3A%22ACME+Corp%22%7D%5D HTTP/1.1
Host: bank.example
```

(URL-decoded `authorization_details` is the JSON shown above.)

**Token response carries `authorization_details` back:**

```json
{
  "access_token":       "eyJhbGciOi...",
  "token_type":         "Bearer",
  "expires_in":         3600,
  "scope":              "openid",
  "authorization_details": [{
    "type": "payment_initiation",
    "actions": ["initiate"],
    "instructedAmount": {"currency": "GBP", "amount": "500.00"},
    "creditorName": "ACME Corp"
  }]
}
```

**Issued access token (JWT) carries it as a claim:**

```json
{
  "iss": "...", "sub": "...", "aud": "...", "exp": ..., "iat": ...,
  "client_id": "psp-1",
  "scope": "openid",
  "authorization_details": [{
    "type": "payment_initiation",
    "actions": ["initiate"],
    "instructedAmount": {"currency": "GBP", "amount": "500.00"},
    "creditorName": "ACME Corp"
  }]
}
```

**RS validates the actual operation against the token:**

When the PSP calls `POST /payments` with that token, the RS verifies:
- Token signature + standard JWT validation
- `authorization_details` includes a `payment_initiation` entry
- The actual payment in the request matches `instructedAmount`,
  `creditorName`, etc. in the token

Mismatch → reject. The bank issues *exactly* the authorization that was
asked for.

## Where it lands on the OAuth abstraction

- **L6 request integrity.** Not because RAR adds signatures (it doesn't),
  but because it tightens the contract — what was asked is exactly what
  was granted.
- **T1, T5, T7.** RAR data crosses the whole request lifecycle, unlike
  PAR/JAR which only touch T1.
- **AS metadata field**: `authorization_details_types_supported` lists
  the `type` values the AS accepts. OneAuth's `ASServerMetadata` already
  has this.

## OAuth 2.0 status

Published 2023. Adopted by Open Banking (UK, EU PSD2, Australia, Brazil),
some healthcare profiles, and emerging in financial APIs more broadly.
Not yet mainstream in consumer OAuth, but the design wins are clear
enough that adoption is growing.

## OAuth 2.1 status

Not mandated by 2.1. Optional. The spec is referenced as the right
mechanism for transaction-specific authorization. FAPI 2.0 mandates RAR
for payment-initiation use cases.

## When NOT to use it

- **Simple capability-based APIs** where "user can read their own
  profile" is the full authorization story. `scope=profile` is exactly
  right; RAR would be over-engineered.
- **Internal services without transaction-specific concerns.** RAR's
  expressivity is wasted.
- **Deployments without a clear `type` schema.** Inventing custom RAR
  types without a profile is hard to maintain. If you don't have a
  regulator or industry profile, you're probably premature in adopting
  RAR.

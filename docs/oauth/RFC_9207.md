# RFC 9207 — OAuth 2.0 Authorization Server Issuer Identification

> **Status:** Standards Track
> **Published:** 2022-03
> **L-tier / T-tier:** L2 · T4 (redirect back)
> **OneAuth coverage:** Implemented (`apiauth/authorize.go` `EmitIssParameter`)
> **See also:** [`RFC_9700.md`](RFC_9700.md) · [`RFC_8414.md`](RFC_8414.md) · [`LANDSCAPE.md`](LANDSCAPE.md)

## In one sentence

RFC 9207 adds an `iss` query parameter to the redirect from `/authorize`
back to the client — a tiny piece of context the client can verify against
its expected AS, closing the mix-up class of attacks.

## What problem does it solve?

| Without 9207 | With 9207 |
|---|---|
| Client receives a `code` on its callback but doesn't know which AS issued it | Client reads `iss` from the redirect query string and checks it matches the AS it sent the user to |
| Mix-up attacks (compromised proxy swaps discovery doc so user authenticates at the wrong AS) succeed silently | Client detects the wrong issuer before exchanging the code at `/token` |
| Multi-tenant clients with several upstream ASes have to infer issuer from state | One query parameter — explicit, machine-readable |

9207 is one of the smallest RFCs in OAuth — six pages of normative text. The
fix is one query string parameter and one verification line of client code.
That's the entire spec.

## Relatable example

A budgeting app supports linking accounts from two banks. The user clicks
"Connect Bank A." A compromised reverse proxy swaps Bank A's discovery
metadata to point `/authorize` at Bank B's URL. The user, expecting Bank A,
logs in at Bank B (who looks just like Bank A). Bank B issues a `code` and
redirects to the budgeting app's callback.

**Without 9207**, the budgeting app gets `?code=xxx&state=yyy` — no way to
tell which bank just issued the code. It POSTs to Bank A's `/token` (per
its stored config), Bank A rejects (the code is from Bank B). Or worse, the
attacker arranged the discovery swap such that the budgeting app *also*
uses Bank B's `/token`, gets a token, treats it as Bank A's token. User's
Bank A view is now showing Bank B account data.

**With 9207**, the redirect carries `?code=xxx&state=yyy&iss=https://bankB.com`.
Budgeting app sees `iss` mismatches the expected `https://bankA.com` —
aborts before any token exchange. Attack fails.

## Key concepts

1. **The `iss` query parameter is the entire wire spec.** It carries the
   issuer URL of the AS that just authenticated the user — the same URL
   that's in the AS's discovery metadata `issuer` field.
2. **Two checks the client must do** (§2.4):
   - `iss` matches the issuer the client expected (the one it used for
     this auth request)
   - `iss` matches the value the client previously received in the AS's
     discovery doc
3. **Errors get `iss` too** — even error redirects carry it, so the client
   can verify "this is a legit error from the expected AS" vs "a
   redirect-spoof error from an attacker."
4. **AS metadata advertisement** (RFC 8414's
   `authorization_response_iss_parameter_supported`) lets clients know
   whether to *require* `iss` (some IdPs ship 9207; others don't).
5. **Backward compatible.** Clients that ignore unknown params and ASes
   that don't emit `iss` interoperate fine. The defense is opt-in by
   each side; both sides supporting it closes the attack.

## Wire example

**Successful auth-code redirect with `iss`:**

```http
HTTP/1.1 302 Found
Location: https://client.example.com/cb?code=Spl...&state=xyz&iss=https://as.example.com
                                                                  ^^^^^^^^^^^^^^^^^^^^^^^^^^
```

**Error redirect (per §3) also carries `iss`:**

```http
HTTP/1.1 302 Found
Location: https://client.example.com/cb?error=invalid_scope&state=xyz&iss=https://as.example.com
```

**Client verification (pseudocode):**

```python
expected_issuer = "https://as.example.com"
actual_issuer = request.GET["iss"]

if actual_issuer != expected_issuer:
    abort("mix-up attack — refusing to exchange code")
```

That's the whole defense. One string comparison.

## Where it lands on the OAuth abstraction

- **L2 lifecycle & discovery.** 9207 is the runtime check that pairs with
  8414's discovery — discovery says "I am issuer X"; 9207 lets the client
  verify "yes, the AS that just answered IS issuer X."
- **T4 (redirect back).** The check fires after the AS responds, before
  the code is exchanged at the token endpoint.
- Named in [RFC 9700 §4.4](RFC_9700.md) as the canonical defense against
  the §4.4 mix-up attack family.

## OAuth 2.0 status

Published 2022 — not part of bare 6749. Optional under 2.0 but strongly
recommended by RFC 9700 (BCP). Adoption is climbing — major IdPs and
client SDKs have been adding support since 2023.

## OAuth 2.1 status

Required by OAuth 2.1 for new deployments (per OAuth 2.1 §4.1.2). Both
emission (AS side) and verification (client side) are mandated.

## Migration path (no-9207 → 9207)

For ASes:

1. **Add the parameter to successful redirects.** Append
   `&iss=<issuer-URL>` to the `Location` header on both code and error
   redirects.
2. **Advertise support** in AS metadata:
   `authorization_response_iss_parameter_supported: true`.
3. **Keep both client populations working.** Old clients ignore unknown
   params; new clients verify.

For clients:

1. **Read `iss` from the redirect query string** if present.
2. **Verify against the expected issuer** before exchanging the code.
3. **Fall back to "is the AS advertised as supporting it?"** — if so,
   missing `iss` is an attack signal; otherwise it's a legacy AS.

The asymmetry — AS can ship support unilaterally, client benefits if it
opts in — means there's no chicken-and-egg. ASes that ship support help
all their clients incrementally.

## When NOT to use it

You will always ship 9207 emission on a new AS — it's free and unlocks the
defense for any client that opts in. The only carve-out:

- **AS deployments that don't have an `/authorize` endpoint at all** (pure
  back-channel grants — client_credentials, jwt-bearer, device flow). The
  mix-up attack family doesn't apply where there's no redirect.

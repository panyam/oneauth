# RFC 6749 — The OAuth 2.0 Authorization Framework

> **Status:** Standards Track
> **Published:** 2012-10
> **L-tier / T-tier:** L0 · T2 + T5 (foundational across T0–T8)
> **OneAuth coverage:** Implemented (token endpoint + `/authorize` via PR 297)
> **See also:** [`LANDSCAPE.md`](LANDSCAPE.md) · [`RFC_oauth21.md`](RFC_oauth21.md) · [`RFC_9700.md`](RFC_9700.md)

## In one sentence

RFC 6749 is *the* OAuth framework — it defines the four roles, two endpoints,
and a set of grant types, plus an error-response shape that every later RFC
builds on. **OAuth 2.1 doesn't replace 6749; it constrains it.**

## What problem does it solve?

| Without 6749 | With 6749 |
|---|---|
| Every API rolls its own delegation flow (Flickr auth, Yahoo BBAuth, Google AuthSub, the original Twitter OAuth-1.0a, vendor-specific tokens everywhere) | One framework for *delegating* access without sharing passwords |
| Apps store user passwords ("give me your Gmail password and I'll fetch your contacts") | Tokens are scoped, expirable, revocable, and never include the user's password |
| Different apps can't share the same identity surface; users re-enter credentials per service | One AS issues tokens that many resource servers honor |

6749 was the spec that made "Sign in with X" universal. It also has *six* error
codes that show up in every later OAuth RFC (`invalid_request`,
`invalid_client`, `invalid_grant`, `unauthorized_client`,
`unsupported_grant_type`, `invalid_scope`) — these are part of the framework
contract.

## Relatable example

When you click **"Sign in with GitHub"** on a third-party CI dashboard:

- *You* are the **resource owner**; the CI dashboard is the **client**; GitHub
  is the **authorization server (AS)**; the GitHub API is the **resource
  server (RS)**.
- Your browser hits `https://github.com/login/oauth/authorize?response_type=code&...`
  (the AS's `/authorize` endpoint — §3.1).
- After you click "Authorize," GitHub redirects back to the CI dashboard's
  callback with `?code=abc&state=xyz` (auth-code grant — §4.1).
- The CI dashboard's backend POSTs that `code` to
  `https://github.com/login/oauth/access_token` (the AS's token endpoint —
  §3.2) with its client credentials and gets back `{access_token, scope,
  token_type}`.
- The dashboard calls `https://api.github.com/user/repos` with
  `Authorization: Bearer <token>` (the RS — §7, governed by RFC 6750).

Every word in this walkthrough is 6749 terminology. Every later RFC slots
into one of those steps.

## Key concepts

1. **Four roles** — resource owner, client, AS, RS. The AS+RS *may* be
   the same server (often are); they're separate roles, not separate processes.
2. **Two AS endpoints** — `/authorize` (browser, redirect-based, §3.1) and
   `/token` (back-channel, POST, §3.2). The split is *not* incidental:
   `/authorize` runs in front of a human; `/token` runs in front of a
   machine. The security models differ.
3. **Grant types are an open registry** — 6749 ships five; every other "give
   me a token" RFC plugs a new `grant_type` value into `/token`. See OneAuth
   coverage below for the full set.
4. **Two client kinds** — confidential (has a server backend that can hold a
   secret) and public (browser SPA, mobile app — can't keep a secret).
   Confidential clients authenticate at `/token`; public ones use PKCE.
5. **Refresh tokens are optional but how everything stays alive** — short-lived
   access tokens + long-lived refresh tokens lets you cap blast radius without
   forcing the user back to the AS every hour.
6. **`state` parameter is your CSRF defense** — the only thing the client gets
   to bind into the redirect that survives the round-trip; cite RFC 9700 §4.7
   for why it's mandatory in practice.

### The five grants 6749 originally shipped (and what happened to them)

| 6749 grant | Status today | OAuth 2.1 verdict |
|---|---|---|
| `authorization_code` (§4.1) | The workhorse — every browser/mobile login | Mandatory + PKCE required |
| `implicit` (§4.2) | Token returned directly to browser via redirect fragment | **Removed** in 2.1 — token leakage via URL |
| `password` / ROPC (§4.3) | Username+password sent to `/token` directly | **Removed** in 2.1 — defeats the point of delegation |
| `client_credentials` (§4.4) | Machine-to-machine; no user involved | Mandatory; widely used for service auth |
| `refresh_token` (§6) | Trade an expiring refresh token for new access token | Mandatory + 9700 §4.14 rotation |

Plus the extension mechanism (§4.5) — `grant_type=<URI>` for new grants — is
how RFC 7523 (jwt-bearer), RFC 8693 (token-exchange), and RFC 8628 (device)
later plug in.

## Wire example

The canonical auth-code flow, post-PKCE (this is what `/authorize` does today
in OneAuth):

```http
GET /authorize?response_type=code
              &client_id=s6BhdRkqt3
              &redirect_uri=https%3A%2F%2Fclient.example.com%2Fcb
              &scope=read+write
              &state=xyzABC
              &code_challenge=E9Mel...               ← RFC 7636 (PKCE)
              &code_challenge_method=S256
HTTP/1.1
Host: as.example.com
```

```http
HTTP/1.1 302 Found
Location: https://client.example.com/cb?code=SplxlOBeZQQYbYS6WxSbIA
                                       &state=xyzABC
                                       &iss=https://as.example.com   ← RFC 9207
```

```http
POST /api/token HTTP/1.1
Host: as.example.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https%3A%2F%2Fclient.example.com%2Fcb
&code_verifier=dBjftJeZ...                                ← PKCE verifier
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "scope": "read write"
}
```

The shape of this response — `{access_token, token_type, expires_in,
refresh_token, scope}` — is 6749 §5.1. Every later grant returns the same
envelope.

## Where it lands on the OAuth abstraction

- **L0 spine.** 6749 *is* the framework; L1–L8 plug into its slots.
- **T-tier: T2 + T5 primarily.** `/authorize` is T2 (browser redirect);
  `/token` is T5 (back-channel exchange). But 6749 also defines the redirect-
  back shape (T4) and the bearer-presentation contract that 6750 fills in (T6).
- 6749 is *deliberately small.* Most things it doesn't specify — token format,
  client auth, discovery, sender binding — were left as extension slots and
  now have their own RFCs (see [LANDSCAPE.md §2](LANDSCAPE.md#2-the-slots-abstraction--implementation)).

## OAuth 2.0 status

**6749 *is* OAuth 2.0.** Every grant, error code, endpoint, and parameter
named in this doc is part of OAuth 2.0 as published in 2012, still the
Internet Standard the production world deploys against. None of it is
deprecated. The five original grants are all still 2.0-legal.

That said, "pure 6749" is almost no one's deployment in 2025. Real-world 2.0
ASes layer:

- RFC 6750 for the bearer-token contract (shipped same day)
- RFC 7636 (PKCE) for code-injection defense — recommended by 9700, mandatory
  in many vendor profiles (Google requires it, Apple Sign-In requires it,
  most modern SDKs default-on it)
- RFC 9700 (Security BCP) for the accumulated wisdom
- RFC 8414 (AS Metadata) for discovery

So when this doc says "Implemented" against 6749, treat it as "the framework
contract is built"; the per-feature 2.0 vs 2.1 nuance lives in
[`RFC_oauth21.md`](RFC_oauth21.md).

## OAuth 2.1 status

OAuth 2.1 is a *constraining* layer on 6749 — it doesn't replace it. The
draft removes implicit (§4.2) and ROPC (§4.3), mandates PKCE (RFC 7636) for
all auth-code exchanges, requires exact redirect URI matching, and forbids
bearer tokens in query strings. The wire is still 6749's wire; the
*requirements* are tighter.

See [`RFC_oauth21.md`](RFC_oauth21.md) for the full diff and OneAuth's
posture, and [`docs/OAUTH21_ALIGNMENT.md`](../OAUTH21_ALIGNMENT.md) for the
row-by-row audit.

## When NOT to use it

You won't use *bare* 6749 in a new deployment in 2025 — you'll layer 6750 +
7636 + 9700 on it as a minimum. But 6749 itself stays the foundation; you're
adding defenses, not replacing the framework. Treat 6749 as the chassis, not
the finished car.

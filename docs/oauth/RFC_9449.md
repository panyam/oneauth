# RFC 9449 — OAuth 2.0 Demonstrating Proof-of-Possession at the Application Layer (DPoP)

> **Status:** Standards Track
> **Published:** 2023-09
> **L-tier / T-tier:** L5 · T5 (issue) + T6 (present proof) + T7 (verify)
> **OneAuth coverage:** Gap (candidate for L5 work)
> **See also:** [`RFC_8705.md`](RFC_8705.md) · [`RFC_9068.md`](RFC_9068.md) · [`LANDSCAPE.md`](LANDSCAPE.md)

## In one sentence

DPoP binds an access token to a key the *client itself* generates — letting
public clients (browsers, mobile apps, CLIs without PKI) get the same
"useless if stolen" property as mTLS-bound tokens, without any PKI
infrastructure.

## What problem does it solve?

| Without DPoP | With DPoP |
|---|---|
| Public clients (browsers, mobile apps) can't use mTLS-bound tokens — no TLS client cert | Client generates its own ephemeral keypair; proves possession via signed proof JWT |
| Bearer tokens leaked from a mobile app's keychain are usable from anywhere | Stolen token without the matching private key is useless |
| FAPI 2.0 requires sender-constrained tokens, but PKI is impractical for consumer apps | DPoP gives FAPI-grade binding without PKI |
| Sender-binding for high-scale public APIs requires a separate proof per request anyway | DPoP makes that proof a tiny signed JWT in a header — cheap |

DPoP is the *public-client* answer to "how do we get sender-binding without
PKI?" It pairs naturally with PKCE — same threat model (public client, no
durable secret), same defense pattern (per-flow ephemeral key, proof of
possession).

DPoP is newer than mTLS (2023 vs 2020) and the design benefits — both as
a spec (`nonce` for replay defense built in) and as deployment ergonomics
(no PKI to manage).

## Relatable example

A mobile banking app that needs FAPI 2.0 compliance:

1. On startup, the app generates an EC P-256 keypair in the keychain.
2. When initiating OAuth, the app sends a *DPoP proof JWT* in a header:
   `DPoP: <signed-JWT-binding-to-this-key>`. The AS issues an access token
   with `cnf.jkt` = thumbprint of the app's public key.
3. Every API call to the RS includes both the access token AND a fresh
   DPoP proof JWT signed with the same key, bound to that specific
   request's method + URL.
4. RS verifies: token signature (via JWKS), proof signature (via key
   embedded in proof header), `cnf.jkt` matches the proof key's
   thumbprint, request method+URL match the proof's claim.
5. If anyone steals the access token, the proof can't be forged without
   the private key.

The public/private key never leaves the app. No PKI. No CA. Same sender-
constraint as mTLS.

## Key concepts

1. **The DPoP proof JWT** is signed by a key the client controls. Its
   header has `typ:"dpop+jwt"`, an embedded `jwk` (the public key), and
   `alg`. Its claims include:
   - `jti` — unique per proof (replay defense)
   - `htm` — HTTP method (e.g., `POST`, `GET`)
   - `htu` — HTTP target URI (e.g., `https://as.example.com/api/token`)
   - `iat` — issued at (timestamp)
   - `ath` — (when binding to an access token) SHA-256 of the access token
   - `nonce` — (when server demanded one) AS-provided nonce echoed back
2. **Two binding points:**
   - At `/token`: AS issues an access token with `cnf.jkt` = thumbprint
     of the proof key (RFC 7638 thumbprint, per [RFC 7517](RFC_7517.md)).
   - At the RS: every request carries a DPoP proof bound to (method, URL,
     access-token hash); RS verifies the proof key matches `cnf.jkt`.
3. **Nonce protocol (§8 + §9)** for replay defense:
   - AS or RS can respond `401 Unauthorized` with
     `DPoP-Nonce: <value>` and `WWW-Authenticate: DPoP error="use_dpop_nonce"`
     when it wants a server-provided nonce in the next proof.
   - Client includes `nonce` claim in the next proof; server records and
     enforces single-use.
   - Without nonce, the `jti`-only defense is bounded by the server's
     clock-skew window.
4. **Token type changes from `Bearer` to `DPoP`** in the Authorization
   header: `Authorization: DPoP <access-token>`. RSes that don't speak
   DPoP would ignore it; RSes that do, validate the proof.
5. **Discovery advertisement**:
   - `dpop_signing_alg_values_supported` in AS metadata
   - `dpop_bound_access_tokens_required` in PR metadata (RFC 9728)
6. **Public clients ≠ unsigned clients.** DPoP is the public-client
   analogue of `private_key_jwt` — both are asymmetric proof-of-possession,
   but DPoP uses an ephemeral client-generated key rather than a registered
   one.

**At `/token`** — client presents DPoP proof, AS issues token with cnf binding:

Decoded DPoP proof JWT:
```

            "jwk": { "kty":"EC", "crv":"P-256", "x":"...", "y":"..." } }
payload : { "jti":"hud8-tbd6-...", "htm":"POST", "htu":"https://as.example.com/api/token",
            "iat":1717000000 }
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "access_token": "eyJhbGciOi...",
  "token_type":   "DPoP",
  "expires_in":   3600,
  "scope":        "read write"
}
```

Issued JWT includes:
```json
{
  "iss": "https://as.example.com", "sub": "user-42", ...,
  "cnf": {
    "jkt": "AaXf2WnsoFn7zCUcr3...thumbprint-of-proof-key"
  }
}
```

**At the RS** — client includes a fresh DPoP proof bound to this request:

```http
GET /api/me HTTP/1.1
Host: api.example.com
Authorization: DPoP eyJhbGciOi...
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2IiwiandrIjp7...}.eyJqdGkiOiJyZG52aGstNDQyIiwiaHRtIjoiR0VUIiwiaHR1IjoiaHR0cHM6Ly9hcGkuZXhhbXBsZS5jb20vYXBpL21lIiwiaWF0IjoxNzE3MDAxMDAwLCJhdGgiOiJTLU0xanBzZ3o2Z3VTU3VkVTM..."}.signature
```

Decoded RS-side proof:
```
header  : { "typ":"dpop+jwt", "alg":"ES256", "jwk": {...same as before} }
payload : { "jti":"rdnvhk-442", "htm":"GET", "htu":"https://api.example.com/api/me",
            "iat":1717001000, "ath":"S-M1jpsgz6guSSudU3..." }
```

RS algorithm:
1. Verify JWT signature on access token (via JWKS).
2. Verify DPoP proof signature (via `jwk` in proof header).
3. Compute thumbprint of `jwk`; compare to access token's `cnf.jkt`.
   Mismatch → reject.
4. Verify `htm` matches request method.
5. Verify `htu` matches request URL.
6. Verify `ath` matches SHA-256 of access token.
7. Check `jti` against replay store; record if first-seen.

## Where it lands on the OAuth abstraction

- **L5 token sender constraint.** DPoP is the public-client / no-PKI path.
- **T5 (issue)** + **T6 (present proof on every request)** + **T7
  (verify proof + cnf match)**.
- Sibling spec: **[RFC 8705 mTLS](RFC_8705.md)** — same property
  (sender constraint) via TLS rather than app layer. Choose by deployment
  topology.

## OAuth 2.0 status

Published 2023. Brand new in OAuth terms. Adoption climbing — Auth0 ships
DPoP support, Microsoft is adding it, FAPI 2.0 includes it as a peer to
mTLS. Not yet universal but the trajectory is clear.

## OAuth 2.1 status

Not mandated by 2.1. FAPI 2.0 (which builds on 2.1) requires one of mTLS or
DPoP. For non-FAPI 2.1 deployments, DPoP is optional but increasingly
recommended for public clients — RFC 9700 §4.10 names sender constraint
generally as a defense; DPoP is its public-client embodiment.

## Migration path (bearer → DPoP-bound)

Easier than mTLS — no PKI. The lift is at the wire-protocol level.

1. **Decide which surfaces use DPoP** — most deployments enable for
   public clients first (mobile apps, SPAs), keep confidential clients
   on `private_key_jwt`.
2. **Client SDK side**: generate ephemeral keypair at startup; sign proof
   JWTs per request; cache + replay-defend `jti`.
3. **AS side**: validate DPoP proof at `/token` (proof signature, `jti`
   uniqueness, `htm`/`htu` match the request, `iat` within window); emit
   `cnf.jkt` claim on issued tokens; change `token_type` from `Bearer`
   to `DPoP`.
4. **RS side**: validate access token (as today) + DPoP proof on every
   request (signature, `jkt` match, `htm`/`htu` match, `ath` match,
   `jti` replay).
5. **Nonce protocol** is a Phase 2 — useful but not required out of
   the gate. Without it, `jti` + short window does the job.

Co-exist with Bearer tokens during the transition: AS issues both shapes
depending on whether the client sent a DPoP proof.

## When NOT to use it

- **Server-to-server with PKI already in place** — mTLS is the simpler
  fit; you're already running the cert plumbing.
- **High-throughput internal services on a trusted network** — proof
  generation is cheap but non-zero; if the network's already controlled,
  the marginal value may not justify the implementation cost.
- **Clients on resource-constrained hardware** (some IoT) that can't
  reliably sign proofs per request.

## OneAuth status

| 9449 surface | Status | Where (grep-verified) | Notes |
|---|---|---|---|
| DPoP proof JWT validation at `/token` | **Gap** | No DPoP handlers anywhere in `apiauth/` | Foundation for everything else |
| `cnf.jkt` claim emission on issued tokens | **Gap** | — | RFC 7638 thumbprint already available via `utils/jwk_thumbprint.go` |
| `token_type: "DPoP"` in token response | **Gap** | — | OneAuth always returns `Bearer` today |
| RS-side proof validation (every request: `htm`, `htu`, `ath`, `jti`) | **Gap** | — | New middleware needed |
| `cnf.jkt` thumbprint match at RS | **Gap** | — | Symmetric to issuance |
| Nonce protocol (`DPoP-Nonce` header) | **Gap** | — | Phase 2; not required for v1 |
| `Authorization: DPoP <token>` parsing | **Gap** | `apiauth/middleware.go:289–292` parses only `Bearer` | Token-type-aware extraction |
| `dpop_signing_alg_values_supported` AS metadata | **Gap** | `apiauth/as_metadata.go` lacks the field | Tracked separately under the mTLS doc too |
| `dpop_bound_access_tokens_required` PR metadata | **Gap** | `apiauth/protected_resource.go` lacks the field | Tracked under [RFC_9728.md](RFC_9728.md) |
| Crypto primitive: RFC 7638 thumbprint | **Implemented** | `utils/jwk_thumbprint.go:19–82` — RSA + EC supported | Reusable when DPoP lands |

**Implementation sketch.** OneAuth already has the JWK thumbprint primitive
(`utils/jwk_thumbprint.go`) — the building block for `cnf.jkt`. The
remaining work is:

1. A `TokenBindingValidator` interface (shared seam with mTLS) — both
   `cnf.jkt` (DPoP) and `cnf.x5t#S256` (mTLS) plug in behind one
   interface.
2. A `DPoPProofValidator` for the proof-JWT-per-request logic with a
   pluggable `JtiStore` (the existing `JTIStore` from
   `apiauth/client_authenticator.go` may be reusable here too).
3. AS metadata fields added incrementally.
4. PKCE pairs *naturally* with DPoP — both are per-flow ephemeral
   asymmetric defenses. A future "FAPI 2.0 strict mode" toggle in
   OneAuth would enable PKCE + DPoP + PAR + JAR together.

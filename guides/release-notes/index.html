OneAuth Release Notes ¶

Version 0.3.21 ¶

This release adds oauth2/oidc/oidctest, a fake OpenID Provider for testing an app’s sign-in wiring. It also fixes a device-flow bug the fake found. A denied CLI sign-in through oauth2/oidc kept polling until the device code expired. The OAuch security analysis now runs in make conformance, so no conformance suite is left to run by hand.

Contract changes ¶

  • New package oauth2/oidc/oidctest (issue 566, PR 568). oidctest.New(t, oidctest.WithClient(id, secret, redirectURIs...)) starts a fake issuer on an httptest.Server.
    • It serves discovery, an RS256 JWKS, the code flow with S256 PKCE, the device flow (RFC 8628), RP-initiated logout and a Graph getMemberObjects route.
    • AddUser makes a person, and SignInAs picks who the next /authorize signs in. Approve(userCode, sub) and Deny answer a device code.
    • WithGroupsOverage leaves groups out of ID tokens the way Entra ID does. EntraGroups{GraphURL: iss.GraphURL()} resolves them through the fake.
    • WithDiscovery, WithIDTokenClaims and WithTokenResponse edit what the fake sends, for negative tests.
    • The fake redirects only to a registered URI that matches exactly. It answers slow_down to a device poll that comes sooner than its interval, as Keycloak does.
  • oidc.New sets the token endpoint’s auth style from discovery (PR 568). Before, x/oauth2 probed. It resent every failed token request in the other auth style straight away. In the device flow every pending or denied poll fails, so each poll went out twice. Keycloak answered the second copy with slow_down. A denied sign-in then polled until the code expired, and a pending one waited 5 seconds longer on every poll.
    • Now oidc.New picks the style through client.SelectAuthMethod from token_endpoint_auth_methods_supported, as LoginWithBrowser does.
    • Token requests now go out in one style. A provider that advertises client_secret_basic but only accepts the secret in the form body would now fail. Keycloak, Entra ID, Okta and Google all accept Basic.

Interop and conformance ¶

  • tests/keycloak/oidctest_parity_test.go sends the same code-flow and device-flow requests to oidctest and to Keycloak. It checks that both give the same error codes (PR 568). TestKeycloakOIDCSignIn_DeviceFlowDenied covers the denied CLI sign-in against Keycloak.
  • tests/oauch drives OAuch’s dashboard with playwright-go (issue 567, PR 569). It imports a site, runs the test set, handles each popup, waits out the timed tests, and checks every result against tests/oauch/expected.yaml. A test missing from the file that doesn’t pass fails the suite. oauch moves from manual to info in conformance/suites.yaml. The first automated run reports 133 tests, with 87 passed and 46 known.

Version 0.3.20 ¶

This release adds two helpers to the oauth2 module for apps that sign people in with GitHub or Entra ID. GitHubHostsFor maps a GitHub API root to the hosts and endpoints a sign-in needs. AllowList.Resolve fetches an Entra user’s groups from Microsoft Graph when the ID token leaves them out. ID tokens now carry a jti, and Keycloak verifies oneauth’s PS256 ID tokens in the interop suite. make release now bumps the test modules too, so make testkcl works after a release without a manual fix.

Contract changes ¶

  • New oauth2.GitHubHostsFor(api) and oauth2.GitHubHosts (issue 554, PR 561). Give it an API root for github.com, a GitHub Enterprise Server host (<host>/api/v3) or GHE.com (api.<tenant>.ghe.com). It returns the web host, the API root, the OAuth endpoint with the device flow, and the /user URL. It refuses a non-https URL unless the host is loopback, and it refuses credentials, a query or a fragment. SetEnterpriseURL uses it and sets the same URLs as before.
  • New oidc.AllowList.Decide, Decision and Rule (issue 555, PR 561). Decide says which rule let a person in: subject, email domain, hosted domain or group. It sets GroupsOverage when Entra left groups out because the person is in too many. Allows still returns a bool and delegates to it.
  • New oidc.AllowList.HostedDomains (issue 555, PR 561). It matches Google’s hd claim.
  • New oidc.AllowList.Resolve, GroupsSource and EntraGroups (issue 555, PR 561). Resolve calls the source only when nothing matched, overage is set, and the list has groups. EntraGroups posts to Graph’s /me/getMemberObjects with the sign-in’s access token. When the source fails, Resolve refuses and returns the error.
  • ID tokens carry a random jti (issue 563, PR 565). It’s 32 random bytes, hex encoded, and new on every token. A relying party that takes the ID token as an RFC 7523 assertion can now refuse a replay. Keycloak’s JWT Authorization Grant needs one unless its identity provider allows reuse.

Interop and conformance (issue 558, PR 562) ¶

  • The OIDF FAPI 2.0 plan’s first client registers a PS256 key, and the second keeps ES256. The harness now runs ensure-signed-client-assertion-with-RS256-fails, and it passes. The plan is at 46 of 52 modules passed, with 4 in review and 2 warnings, all accepted gaps.
  • TestKeycloak_VerifiesOneauthPS256IDToken has Keycloak 26.6 exchange a oneauth PS256 ID token through its JWT Authorization Grant. Keycloak refuses the same claims under another key, as RS256, or a second time.

Release tooling (issue 553, PR 564) ¶

  • make release moves the oneauth requires in the unpublished modules (tests/*, docs/site) to the new version. Before, tests/keycloak fell one version behind at each release, and make testkcl stopped at updates to go.mod needed.
  • verify-submodule-deps checks that every unpublished module resolves with GOWORK=off. make test runs it, and CI’s lint job now does too.

CI (PR 560) ¶

  • The core and sub-module tests run as a parallel matrix of OS and group.

Version 0.3.19 ¶

This release adds PS256 as an authorization-server signing algorithm, which FAPI 2.0 allows where RS256 isn’t. The client SDK and CLI now carry every client metadata field the DCR endpoint does. Relative links on the docsite stop 404ing.

Contract changes ¶

  • jwt.signing_alg: PS256 / OneAuthConfig.SigningAlg: "PS256" (issue 330, PR 559). An RSA key signs access tokens, ID tokens, JARM responses and signed userinfo with RSASSA-PSS, and the JWKS lists the key as PS256. One key still signs under one algorithm, so an RS256 server can’t sign PS256 for a single client.
  • utils.IsAsymmetricAlg includes PS256 (PR 559). The JWKS handler publishes PS256 records, the registrar stores PS256 client keys, and DecodeVerifyKey parses them as RSA. Nothing changes for a deployment that never configures PS256.
  • fapi2 accepts jwt.signing_alg: PS256 as well as ES256 (PR 559). Under fapi2, token_endpoint_auth_signing_alg_values_supported is now [PS256, ES256].
  • New fields on client.ClientRegistrationRequest and ClientRegistrationResponse (issue 557, PR 559). These are JWKS (raw JSON), JWKSURI, TokenEndpointAuthSigningAlg, the logo, policy and terms URIs, SubjectType, SectorIdentifierURI, UserinfoSignedResponseAlg, the back-channel logout pair and AuthorizationDetailsTypes, plus ResponseTypes on the response.
  • New CIMDAppStore.UserinfoSigningAlgs and AuthorizationSigningAlgs (PR 559). A CIMD document asking for a userinfo or JARM algorithm the AS doesn’t sign with is now invalid, where before it failed at the response. NewOneAuth sets both.

PS256 (issue 330, PR 559) ¶

  • ID tokens accept PS256, with at_hash over SHA-256.
  • A client key stored as PS256 authenticates with private_key_jwt.
  • oneauth-server’s code_flow.oidc, code_flow.jarm and key rotation accept PS256, and the ephemeral PS256 key is RSA-2048.
  • make exercise-jarm registers its client with the algorithm the server advertises, so it passes against an ES256 server and against a PS256 one.

Client metadata parity (issue 557, PR 559) ¶

  • A drift test compares the SDK’s DCR structs with the server’s, so the next server field can’t lag.
  • oneauth dcr register and put take --metadata FILE, which sets any RFC 7591 field from JSON, with explicit flags winning. A field the CLI doesn’t know is an error, so a misspelling isn’t dropped silently.
  • CIMD documents carry dpop_bound_access_tokens, require_pushed_authorization_requests and userinfo_signed_response_alg, and the AS enforces them as it does for a registered client.
  • DCR keeps ignoring metadata it doesn’t understand, as RFC 7591 §2 requires, and a test now pins it. The response echoes what was stored.

Docsite (PR 559) ¶

  • Relative links in rendered markdown now point at the page that renders the target, or at the file on GitHub. A build had 501 broken .md links across 52 pages, and now has none.
  • LANDSCAPE.md’s per-RFC template renders as one code block again.

CI and tests ¶

  • CI now runs the cmd/oneauth and docs/site tests. Before, the CLI tests never ran there.
  • tests/keycloak/go.mod follows the root version again (issue 553, which keeps recurring with each release).
  • Not done: an OIDF FAPI 2.0 run with a PS256 client, and Keycloak verifying oneauth’s PS256 tokens (issue 558).

Version 0.3.18 ¶

This release finishes JWT Secured Authorization Response Mode (JARM). A FAPI client can ask for response_mode=jwt and get its authorization response back as one JWT that the AS signs. The client SDK verifies it before it uses the code. make exercise-jarm logs in this way against oneauth-server and against Keycloak, and refuses a response with a tampered signature.

Contract changes ¶

  • New optional OneAuthConfig.JARM (PR 551). Nil, the default, keeps today’s behavior, and the JARM modes stay refused with invalid_request. Set, it needs an RS256 or ES256 key, and NewOneAuth panics on an HMAC secret or an empty issuer.
  • AuthorizationResponse gains Signed and Params() (PR 551). For a JARM response, Mode is the base delivery mode (query.jwt is ResponseModeQuery), and Params() returns the one response parameter. RedirectURL signs too, and it returns an error when signing fails.
  • A JARM response carries RFC 9207 iss inside the JWT, not on the URL (PR 551). A client checking iss on a JARM redirect has to read it from the verified JWT.
  • LoginWithBrowser with a JARM ResponseMode now verifies the response (PR 552). In v0.3.17 it refused every callback. It now takes code and state from a response JWT that passes client.VerifyAuthorizationResponse. A plain code under a JARM mode still fails with ErrUnverifiedAuthorizationResponse.
  • LoginWithBrowser refuses fragment and fragment.jwt before it opens the browser (PR 552). A fragment never reaches the loopback server, so these used to time out.
  • New core.AppRegistration.AuthorizationSignedResponseAlg (PR 556). The gorm store adds a column on the next AutoMigrate. The gae entity and the fs store need nothing.
  • DCR now refuses authorization_signed_response_alg it can’t serve (PR 556). On an AS without JARM that means every value. Before, DCR dropped the field silently and answered 201.

Signed authorization responses at the AS (issue 411, PR 551) ¶

  • /authorize accepts jwt, query.jwt, fragment.jwt and form_post.jwt, through PAR too. jwt means query.jwt for code and fragment.jwt for the implicit types. query.jwt is refused for the implicit types, like query.
  • The JWT carries iss, aud (the client_id), a 60-second exp (JARMConfig.Expiry), state, and the code or error. It’s signed with the AS key, with the kid the JWKS publishes.
  • Errors that go to the redirect_uri are signed too. A response the AS can’t sign shows a server_error page, and never goes out unsigned.
  • AS metadata lists the JARM modes in response_modes_supported, and adds authorization_signing_alg_values_supported (ASServerMetadata.AuthorizationSigningAlgValuesSupported, OneAuth.AuthorizationSigningAlgs).
  • oneauth-server turns it on with code_flow.jarm.enabled, and refuses to start with it under an HMAC key or without the code flow.

Verifying them in the client SDK (issue 412, PR 552) ¶

  • client.VerifyAuthorizationResponse checks a JARM response: an asymmetric signature by a key in the AS’s JWKS, iss equal to the discovered issuer, aud containing the client, and an unexpired exp. Failures wrap ErrUnverifiedAuthorizationResponse.
  • An error inside a verified response comes back as a *CallbackError, like a denial on a plain response.
  • The loopback callback reads a POSTed form, so form_post.jwt works.
  • Keycloak 26’s JARM JWT repeats iss. The last value wins, as encoding/json does, so its responses verify.
  • oneauth token browser --response-mode jwt verifies the response the same way.

Registering the signing algorithm (issue 413, PR 556) ¶

  • A client registers authorization_signed_response_alg through DCR (JARM §3). DCR accepts only AppRegistrar.AuthorizationSigningAlgs, so none is refused. Every app store keeps the field, CIMD documents carry it, and register, read and RFC 7592 update echo it.
  • The AS signs with the client’s registered algorithm. One it can’t sign with fails the response with server_error.
  • Registering an algorithm doesn’t turn JARM on. The client still asks with response_mode=jwt, as Keycloak does. With none registered, the AS uses its own key’s algorithm, not the RS256 JARM §3 names.
  • client.ClientRegistrationRequest and ClientRegistrationResponse get the field, and oneauth dcr register and put get --authorization-signed-response-alg.
  • Not done: PS256 with an RSA key, since the JWKS lists the key under RS256 only (issue 557), and encrypted responses.

Testing and conformance ¶

  • make exercise-jarm passes on both targets, and a third run flips one character of the response signature and must be refused. It runs as the gating jarm suite in make conformance.
  • TestKeycloak_JARMLogin logs in with jwt, query.jwt and form_post.jwt against Keycloak’s PS256 responses.
  • testutil.KeycloakPasswordLogin submits a form_post response page, as a browser’s script would.
  • tests/keycloak/go.mod follows the root version again, after the v0.3.17 and v0.3.18 releases left it behind (issue 553).

Docs and CI ¶

  • A JARM page on the docsite (specs/jarm), linked from the specs index and the nav. The FAPI and landscape pages no longer list JARM as a gap, and the client SDK guide covers ResponseMode.
  • The browser auth guide documents oidc.Provider.LogoutURL from v0.3.17.
  • The vulncheck workflow moves to panyam/ci-actions v0.1.4, which titles the issue it files by what stopped the scan.

Version 0.3.17 ¶

This release lets an app list every API key and sweep the expired ones through the store interface. It also adds OIDC RP-initiated logout, stops the GitHub and Google callbacks from echoing the state cookie, and adds the JARM mission’s exercise.

Contract changes ¶

  • New optional core.APIKeyAdmin (issue 549, PR 550). It has ListAPIKeys and CleanupExpiredAPIKeys. APIKeyStore doesn’t change, so a custom store still compiles. Callers check for the new interface with a type assertion.
  • The gorm APIKeyModel gets an index on expires_at (PR 550). The next AutoMigrate creates it.
  • client.ASMetadata gains EndSessionEndpoint (PR 547).
  • A browser login with a JARM response mode now refuses every callback (PR 548). LoginWithBrowser returns ErrUnverifiedAuthorizationResponse until the SDK can verify signed responses (issue 412).

Listing and sweeping API keys (issue 549, PR 550) ¶

  • ListAPIKeys returns every key in the store, across subjects, with KeyHash empty.
  • CleanupExpiredAPIKeys deletes every key whose ExpiresAt is at or before req.Now, revoked or not. It never deletes a key with no ExpiresAt. A zero Now means the current time, and Removed reports the count.
  • The fs, gorm and gae stores implement it. On fs, a listing skips a key file that another handle deletes mid-scan, where reading the directory directly used to fail.
  • apikeytest.RunAdmin is the shared contract suite for a custom store.

OAuth sign-in (issue 546, PR 547) ¶

  • The GitHub and Google callbacks check state through oauth2.VerifyState. Every state failure answers 400 invalid oauth state. The old error page printed the real oauthstate cookie value.
  • oidc.Provider.LogoutURL(idTokenHint, postLogoutRedirectURI, state) builds the RP-initiated logout redirect from the issuer’s end_session_endpoint, so a sign-out at the app can also end the issuer’s session.

JARM mission exercise (issue 410, PR 548) ¶

  • oneauth token browser takes --response-mode.
  • make exercise-jarm logs in headless with response_mode=jwt against oneauth-server and the test Keycloak realm. It prints each callback and the CLI’s result. Both targets still fail at the step that issues 411 and 412 fix.

Version 0.3.16 ¶

This release adds a sign-in provider for any OpenID Connect identity provider, beside GitHub and Google. It also lets an authorization server behind a TLS-terminating proxy check DPoP proofs and client assertions without pinning its URLs.

Contract changes ¶

  • oauth2 now requires the root module (PR 545). The new oauth2/oidc package imports client and keys for discovery and ID token checks, so go.sum for an oauth2 user lists jwt, fernet and otel. The base oauth2 package still imports nothing from oneauth, so an app using only GitHub or Google compiles none of it.
  • New optional TrustedProxies fields (PR 544). These are OneAuthConfig.TrustedProxies, DPoPConfig.TrustedProxies, and the field of that name on IntrospectionHandler, RevocationHandler and PARHandler. NewTokenEndpointHandler copies OneAuth.TrustedProxies into the handler’s existing field, which also gates X-Forwarded-For for rate limiting. Empty keeps today’s behavior.
  • oauth2 exports RedirectWithPKCE and VerifyState (PR 545). A provider in another package uses them to set and check the same state, PKCE and callback cookies.

Generic OpenID Connect sign-in (issue 542, PR 545) ¶

  • oidc.New(ctx, oidc.Config{Issuer, ClientID, ClientSecret, CallbackURL, HandleUser}) signs people in through Entra ID, Okta, Google Workspace, Keycloak, or any other provider, by issuer URL. It mounts like the GitHub provider.
  • Discovery runs once in New. The JWKS is fetched on first use and again when a token names an unknown kid, so a key rotation needs no restart. The issuer must be https, or http on a loopback host.
  • The browser flow sends PKCE and a nonce. HandleUser runs only after client.VerifyIDToken checks the ID token’s signature, iss, aud, exp, nonce and at_hash, and it receives the token’s claims.
  • DeviceAuth and DeviceAccessToken sign in from a CLI when discovery lists a device endpoint. They send the client secret at the device endpoint, which x/oauth2 leaves out and Keycloak requires for a confidential client.
  • oidc.AllowList decides who may sign in, by verified email domain, a groups value or sub. An empty list allows nobody.
  • oauth2/oidc/example runs both flows against the Keycloak in docker-compose.yml.

Proxied deployments (issue 541, PR 544) ¶

  • core.TrustedProxies.IsHTTPS(r) reports whether the client used https. It is true when r.TLS is set. It is also true when the TCP peer is a trusted proxy and that proxy’s first X-Forwarded-Proto value says https, or else the first Forwarded element’s proto does. From any other peer the headers are ignored.
  • With no pinned EndpointURL or BaseURL, a DPoP validator derives the expected htu from the request. Behind a trusted proxy that says https, the htu is now https, matching the URI the client called (RFC 9449 §4.3).
  • With no AcceptedAudiences, the token, PAR, introspection and revocation endpoints derive the client-assertion audience the same way. X-Forwarded-Host is still never read.

Tests ¶

  • The Keycloak test realm gains email and profile client scopes and the device grant on test-confidential. Run make downkcl before make testkcl so a running container picks up the new realm.
  • Keycloak interop CI now also runs on changes under oauth2/.

Version 0.3.14 ¶

This release lets a client use an https URL it controls as its client_id, through Client ID Metadata Documents (CIMD). The MCP authorization spec asks authorization servers to support them. It also adds the MCP conformance framework’s authorization-server scenarios to make conformance. Every expected outcome in known-gaps.yaml is now marked as an open gap or an accepted one.

Contract changes ¶

  • The token endpoint answers a failed client lookup with an OAuth error instead of 500 (PR 536). The confidential-client check, the dpop_bound_access_tokens lookup and the registered-scope lookup each turned any lookup error other than “not found” into server_error. A bad client metadata document now gets invalid_client, and an unreachable one gets 503 temporarily_unavailable. Other store errors are still 500.
  • Device authorization passes a lookup error’s own status through (PR 536). Only the CIMD errors carry one, so registered clients see no change.
  • New optional fields (PR 536). These are OneAuthConfig.ClientIDMetadataDocuments, ASServerMetadata.ClientIDMetadataDocumentSupported, and AppRegistration.JWKS. AppRegistration.JWKS holds a CIMD client’s inline keys in memory only, and stores never save it.
  • The toolchain is Go 1.27.4 (PR 534). The go lines stay at 1.26.9, so importers keep the same minimum Go.

Client ID Metadata Documents (issue 532, PR 536) ¶

  • OneAuthConfig.ClientIDMetadataDocuments, or code_flow.client_id_metadata_documents on the reference server, turns it on. It’s off by default, and FAPI 2.0 refuses it.
  • apiauth.CIMDAppStore wraps the app store. A client_id that starts with https:// is fetched, checked against draft -03, and cached. So /authorize, the token endpoint, userinfo and the consent page all accept it.
  • The fetch follows no redirect, accepts only a 200, reads at most 5 KB, and dials no private address unless allow_private_client_hosts is set. It caches for the response’s max-age, clamped to between 1 minute and 24 hours.
  • Clients can use none with PKCE, or private_key_jwt with keys in the document’s jwks or at its jwks_uri. A document with a secret or a shared-secret method is refused.
  • The consent page names the host that publishes the document and the host the user returns to. A URL client’s logo_uri isn’t shown.
  • Discovery advertises client_id_metadata_document_supported. The new docsite page specs/cimd/ explains it.

Conformance ¶

  • mcp-auth-as is a new gating suite. It runs the MCP framework’s authorization-server scenarios against oneauth-server, and a headless login approves each authorization request (PR 533, issue 496). It runs once with a registered client and once with a CIMD client, and all 12 checks pass (PR 536).
  • Each known-gaps.yaml entry now has a class. An open entry is a gap with an open issue, and an accepted entry is an outcome oneauth keeps on purpose. The report’s new Known gaps section lists all 24, and make gapcheck fails when an open entry cites a closed issue (PR 535).
  • make up-all, down-all, ps-all and logs-all start and stop every Docker service the tests use, from a top-level docker-compose.yml (PRs 530 and 531, issue 243).
  • A weekly workflow runs make vulncheck over every published module (PR 534).

Version 0.3.13 ¶

This release fixes a regression in 0.3.12. An AS with no AllowedResources refused every authorization-code redemption that named a resource, so MCP clients such as mcpkit’s OAuth token source couldn’t get a token.

Fixed ¶

  • The code grant falls back to the allowlist when the code carries no resources (PR 529). Without an allowlist, /authorize ignores resource and stores none on the code. The token request then narrowed against that empty list and got invalid_target. Now a code with no stored resources checks the token request’s resource against AllowedResources, as the device grant and refresh already did. With no allowlist the AS ignores it, and aud keeps its default. A code with stored resources still narrows as before.

Version 0.3.12 ¶

This release binds access tokens to the RFC 8707 resource a client names, on every grant. It closes the code findings from the OAuch run, adds response_mode=form_post, and lets a user withdraw consent from a connected-apps page. The FS refresh-token store stops keeping tokens in plaintext. Three OIDF plans (Form Post Basic, Implicit and Form Post Implicit) and a third MCP server-auth suite join make conformance.

Contract changes ¶

  • Client credentials in the request URI get a 400 (PR 525). A client_secret, client_assertion or client_assertion_type in the query string of the token, PAR, introspection, revocation or device endpoint is invalid_request. Those endpoints read every other parameter from the body only.
  • A repeated parameter gets invalid_request (PR 525). It used to take the first value. resource and audience may still repeat. At /authorize, a repeated client_id or redirect_uri shows the error page.
  • Code redirects end in #_=_ (PR 525), as RFC 9700 section 4.1.3 suggests.
  • An unknown response_mode gets invalid_request (PR 527). So does query for an implicit response type.
  • MountProtectedResource with a path serves its metadata only at the path URL (PR 524). A resource with no path still gets the root URL. RFC 9728 section 3.3 makes a client discard the root copy of a pathed resource’s document.
  • New stored fields (PR 527). DeviceAuthorization.Resources holds the device flow’s resources, and GAE consent grants gain an indexed subject. GAE grants saved earlier get it on their next read, or all at once from GAEConsentStore.BackfillConsentSubjects (PR 528).
  • GORM RevokeAPIKey returns ErrAPIKeyNotFound for a missing key (PR 528), as FS and GAE already did.
  • error_description text is mapped into RFC 6749’s character set (PR 528). “§” becomes “section”, double quotes become single quotes, and other characters outside printable ASCII become ?. Error codes are unchanged.
  • The FS refresh-token store keeps only hashes (PR 528). Files are named by TokenHash, and new records have an empty token. Older files still load and lose their plaintext on the next rotation or revocation.

Resource indicators (issues 521 and 523) ¶

  • OneAuthConfig.AllowedResources, or jwt.resources on the reference server, lists the resource servers the AS issues tokens for (PR 524). A named resource becomes the access token’s aud, and an unlisted one is invalid_target. With no list the AS ignores resource, as before.
  • Client credentials, the code grant, refresh and implicit honor it (PR 524), and so do the device and password grants (PR 527). A code, device code or refresh token keeps its resources, and a later token request may narrow them but not widen them.
  • trusted_assertion_issuers on the reference server turns on the jwt-bearer and token-exchange grants, with a PEM key or JWKS URI per upstream IdP (PR 524).

Authorization endpoint and consent ¶

  • response_mode=form_post answers with an auto-submitting form, for successes and errors, through consent and PAR (PR 527, issue 500). Discovery lists response_modes_supported. The page escapes every value and allows only its own script, by nonce.

Version 0.1.45 ¶

Token audit (issue 88, PRs 414 to 416) ¶

Issue 88’s third slice walked token validation, revocation and
introspection. The matrix is the “Tokens and keys” section of
docs/SECURITY_AUDIT.md.

  • Validation. exp is required. An empty HMAC key never signs or
    verifies. Logout tokens, ID-JAGs and sessions are refused as access tokens
    by typ header and type claim. A key registered to a client verifies
    only tokens carrying that client_id, and a token with the validator’s own
    kid is checked with its own key (it used to be checked against the
    named client’s key and fail). CustomClaims can’t set nbf, scope,
    azp, sid, act or may_act.
  • Challenges. invalid_token only when a token was presented, 403
    insufficient_scope with scope for a missing scope, and
    resource_metadata from APIMiddleware.ResourceMetadataURL.
  • Revocation. A client revokes only its own tokens (ErrRevokeNotOwner,
    400 invalid_request, as Keycloak answers). Access tokens are verified
    before their jti is blacklisted, a missing token is 400, and every
    token type is searched whatever the hint.
  • Introspection. token_type is Bearer / DPoP, and refresh tokens
    can be introspected (NewTokenIntrospectorWithRefreshStore, wired by
    OneAuth).
  • Grants. jwt-bearer assertions need exp and a configured audience,
    and one with a jti is single-use. A code redeemed by two requests at
    once gives the loser invalid_grant, and tokens from a code carry
    client_id.
  • Refresh tokens. GORM rotation is a compare-and-set, and rotation keeps
    the family’s expiry in every store.
  • Sessions. httpauth and the reference server accept only
    type: session JWTs as logins. The reference server refuses a
    jwt.secret_key under 32 bytes.
  • CodeQL. The three error-level alerts are fixed: no token prefix in
    httpauth’s log, and no unverified JWT parse in the revoker or the
    server’s /api/revoke.

Upgrading ¶

  • Tokens without exp no longer validate. oneauth always set it.
  • Missing scope is 403, not 401.
  • Reference server: jwt.secret_key (JWT_SECRET_KEY) must be at least
    32 bytes, in every signing mode.
  • Tenant-minted tokens must carry their own client_id.
  • Refresh sessions end TokenExpiryRefreshToken (7 days) after login,

  • jwt-bearer / token-exchange: set TrustedAssertionIssuer.Audiences or

The refresh grant used to check only the token, so a leaked refresh token
redeemed under any client_id, or none, and a confidential client’s token
redeemed without its secret (RFC 6749 §6).

    callers of TokenIssuer.RefreshGrant.

    not-found as a 500, where it used to treat the client as public. This also
    reaches jwt-bearer, token-exchange and PAR.

    issued to, and the automatic refresh sends it instead of "cli".

  • Client SDK proofs (PR 379). client.DPoPKey (ES256) mints a proof per

    HMAC NonceSource lets the AS (§8) and the resource server (§9) demand a

    by default.
  • Keycloak interop (PR 385). OneAuth’s middleware accepts a
    Keycloak-issued bound token and refuses it presented as Bearer.

Pushed authorization requests (RFC 9126, PR 381) ¶

POST /par stores the authorization request and returns a request_uri, and
/authorize accepts a request carrying only client_id + request_uri.
Mounted by MountAuthorize when AuthorizeMountConfig.PushedStore is set,
with in-memory and GORM stores. A push may carry a DPoP key in its header or
as dpop_jkt (RFC 9449 §10.1).

Loopback redirects for native clients (PR 388) ¶

  • Caller-owned listener (issue 387). BrowserLoginRequest.Listener takes
    a loopback listener the caller already bound, and
    LoopbackRedirectURI(addr) names the redirect the login will send. A
    client that registers via DCR first registers exactly that string, so an AS
    that matches redirect_uri byte-for-byte accepts it, and nothing can take
    the port between registration and login. LoginWithBrowser closes the
    listener when it returns.
  • RedirectURI sends a registered redirect verbatim (an IP literal, a
    path other than /callback). It must be loopback http with an explicit
    port matching the listener, checked before the browser opens.
  • FollowRedirects fails fast. A 400-or-worse from /authorize now
    returns the AS’s error / error_description. Before, LoginWithBrowser
    sat out its timeout (five minutes by default) waiting for a callback that
    was never coming.
  • ApproveConsent is a headless opener for demo servers that answer
    /authorize with a consent form. It posts the approve button and refuses a
    form without one.
  • Behavior change on the AS (issue 389). /authorize now ignores the port
    when matching an http redirect on 127.0.0.1, [::1] or localhost, as

Version 0.1.37 ¶

DPoP — sender-constrained access and refresh tokens (RFC 9449) ¶

A token can now be bound to a key the client holds, so a leaked token is
unusable by whoever leaks it. Both halves ship together: the authorization
server binds the token, and the resource server refuses to honor it unless the
presenter proves the key.

Everything here is off by default. An existing deployment that wires neither
side behaves exactly as it did in 0.1.36.

Issuance (PR 370). Set OneAuthConfig.DPoP to a DPoPProofValidator and
the token endpoint starts accepting a DPoP proof header on any grant. A
request that carries a valid proof gets cnf.jkt in the access token,
token_type: DPoP in the response, and a refresh token only that key can
rotate. A request with no proof gets exactly what it got before.

  • Proof validation per §4.3: typ, an asymmetric alg allow-list (ES256,
    RS256, PS256 by default; symmetric algorithms can never be enabled), the
    embedded public jwk with private members rejected, the signature, htm,
    htu, an iat window, and jti replay through the existing JTIStore.
  • Refresh-token binding persists in all three backends (FS, GORM, Datastore)
    and is carried forward on rotation. A bound refresh token presented without
    its key is invalid_grant.
  • dpop_signing_alg_values_supported on authorization-server metadata.

Enforcement (PR 372). Set APIMiddleware.DPoP and the resource server
accepts Authorization: DPoP <token> with a per-request proof, checks the
proof’s ath against the presented token, and matches the proof key against
the token’s cnf.jkt.

  • A bound token presented under the Bearer scheme is refused, per §7.2.
    Without that check a thief drops the DPoP header and the binding buys
    nothing.
  • WWW-Authenticate advertises both schemes, with error information on the
    scheme the client actually used.
  • APIMiddleware.RequireDPoP refuses bearer presentations outright, backing
    dpop_bound_access_tokens_required on protected-resource metadata
    (RFC 9728), which lands alongside dpop_signing_alg_values_supported.
  • Introspection responses carry cnf, so a resource server that validates
    remotely enforces the same binding as one validating the JWT locally.

Rollout order. A resource server with APIMiddleware.DPoP unset accepts a
bound token as an ordinary bearer token, which RFC 9449 §7.2 both predicts and
permits. Wire enforcement at the resource servers first, then start issuing
bound tokens. The reverse order leaves a window where the binding protects
nothing.

Deployment note (GORM). The refresh_tokens table gains a
confirmation_jkt column. Run AutoMigrate before deploying. The column is
empty for existing rows, which reads back as an unbound token, so current
behavior is preserved. Datastore adds an equivalent optional property and
needs no migration.

API additions. core.Confirmation (the RFC 7800 cnf claim as a type),
CreateAccessTokenRequest.Confirmation, CreateAccessTokenResponse.TokenType,
RefreshGrantRequest.Confirmation and the same field on each grant request
type, TokenInfo.Confirmation, IntrospectionResult.Cnf, and
IntrospectionValidator.ValidateInfo. The confirmation is a struct rather
than a bare thumbprint string so that mTLS certificate binding (x5t#S256,
issue 335) adds a field instead of a second parameter on every issuance path.

One behavior change without a flag. cnf is now a standard claim, so it
no longer appears in TokenInfo.CustomClaims. Code reading cnf out of the
custom-claims bag should read TokenInfo.Confirmation instead. This also stops
a deployment’s CustomClaimsFunc from writing a binding the server never
verified.

Conformance. Validated against the RFC’s own published vectors: the
Figure 2 proof and the Figure 9 thumbprint it produces, plus the Figure 13
access token and the Figure 14 ath computed from it.

Closes issue 336. Remaining RFC 9449 surface: the nonce protocol (§8, §9) and
dpop_jkt on the authorization request (§10). Keycloak interop for the
resource-server half is issue 371.

Version 0.1.5 ¶

Client SDK — RFC 8693 token exchange + RFC 7523 §2.1 JWT bearer grant ¶

Two new general-purpose OAuth primitives on AuthClient. Both are additive — no existing behavior changes.

AuthClient.TokenExchange(*TokenExchangeRequest) — RFC 8693. Exchange a subject token (plus optional actor token / requested type / audience / resource / scope) for a freshly issued token. Returns TokenExchangeResponse including IssuedTokenType (required by RFC 8693 §2.2). Useful for bridging trust domains — e.g. exchanging an upstream-IdP ID token for an internal ID-JAG.

AuthClient.JwtBearerGrant(*JwtBearerGrantRequest) — RFC 7523 §2.1. Present a signed JWT (typically the output of a prior token exchange or trusted upstream issuance) as assertion at the token endpoint to obtain an access token. Version 0.1.0 (Initial Release) ¶

Overview ¶

Initial release of OneAuth, a Go authentication library providing unified local and OAuth-based authentication with multi-method account linking.

Core Features ¶

  • Three-layer model: Users, Identities, and Channels with global identity verification
  • Local auth: Email/phone + password with bcrypt hashing, configurable validation
  • OAuth integration: Google, GitHub, etc. with automatic identity unification across providers
  • Email verification: Token-based flow with configurable expiry and extensible sender interface
  • Password reset: Secure token-based flow with anti-enumeration (always returns success)
  • Session management: Callback-based (HandleUser) supporting cookies, JWTs, or custom schemes

Storage ¶

  • File-based stores (FS): JSON file storage for Users, Identities, Channels, and Tokens. Suitable for development and small-scale use (<1000 users).
  • Database-agnostic interfaces: UserStore, IdentityStore, ChannelStore, TokenStore for production implementations.

HTTP Endpoints ¶

/auth/login, /auth/signup, /auth/verify-email, /auth/forgot-password, /auth/reset-password. Accepts form-encoded and JSON bodies; returns JSON responses.

Helper Functions ¶

NewCreateUserFunc, NewCredentialsValidator, NewVerifyEmailFunc, NewUpdatePasswordFunc, DetectUsernameType, DefaultSignupValidator, GenerateSecureToken.

Known Limitations ¶

File-based stores not recommended at scale. No built-in rate limiting, CSRF protection, or session storage (application responsibility). Console email sender only.

golang.org/x/crypto/bcrypt, golang.org/x/oauth2 (optional).

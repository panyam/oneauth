# tests/oidf-conformance — OIDF harness gotchas

- **`make testoidf` runs every OIDC and FAPI plan oneauth claims**, each against a fresh server: FAPI 2.0 on `:8889` (issue 339), Basic OP on `:8890` (mission 477), Dynamic OP on `:8891` (issue 493, also with the implicit `RESPONSE_TYPE`s), `oidcc-test-plan` on `:8892` once per client auth method (issue 494), Form Post Basic OP on `:8893` (issue 500, the Basic OP package with another plan name), and Implicit OP on `:8894` and Form Post Implicit OP on `:8896` (issue 526, the Basic OP package with one static implicit client). `:8895` belongs to OAuch. All go through `scripts/exercise-oidf.sh <plan>`, and it refuses to run while something holds a port. A module that doesn't pass needs a whole-module `known-gaps.yaml` entry (`expected-review`, `-skip`, `-warning`, `-fail` or `-manual`; review and warning need `evidence`). A module that waits for a person to press Start gets a `Plan.Actions` entry instead, as `server-rotate-keys` does (it rotates the server's key). `plans: [...]` lets one entry cover a module several plans share. `make exercise-<plan> MODULE=<substring>` runs matching modules.
- **A plan run more than once has a `Plan.Key`** (`oidcc-test-plan-private_key_jwt`). The manifest, the run record and `suites.yaml` use the key, and the harness gets the plan name.
- **The harness `wait` command matches its regex against the element's text**, so wait on an element whose text the regex fits (the consent page's `<h1>Authorize …`), not on a button.
- **A screenshot-only module finishes on the screenshot.** The registration `logo/policy/tos` modules throw if the browser also approves afterwards.
- **A plan is a package plus a case in the script.** `oidfplan` runs any plan and judges it; `fapi2` and `oidcc` only build the plan's clients, variant, config and browser automation. A new plan adds a package, a `case` in `scripts/exercise-oidf.sh` and `cmd/exercise`, a server config, and a ratchet test like `oidcc_plan_test.go`.
- **`make testoidf` reuses whatever answers on `:8888`.** It starts the discovery server with `go run` only when nothing listens, and leaves it running, so a server from another checkout or an older build gets tested. `pkill -f oneauth-server.yaml` before running from a different worktree or after changing server code.
- **The harness nginx serves `certs/harness.crt`, signed by `certs/ca.crt`**, so oneauth-server can fetch a client's `jwks_uri` from it over verified TLS (issue 507). A harness started before that serves the image's self-signed cert, and the jwks_uri modules fail until `make downoidf upoidf`.
- **The harness bind-mounts `certs/` from the checkout that ran `make upoidf`.** Run `make downoidf` before removing that worktree, or the harness loses its truststore. MongoDB lives in the `oidf-conformance_mongo-data` volume, and nginx answers as `localhost.emobix.co.uk` inside the compose network.
- **CI runs `make testoidf` nightly and on demand** (`oidf-conformance.yml`, issue 498), against the harness release pinned in `docker-compose-prebuilt.yml`. A new harness release is a PR that bumps `OIDF_HARNESS_TAG`'s default and rebaselines; the registry's `latest` is older than the releases.
- **Read a module's harness log through the plan ID the run prints** (`/api/plan/<id>`, then `/api/log/<instance>`). Picking the newest instance by plan start time can return an older run's module.
- **`expected-review` evidence is matched against the page's raw HTML**, so markup inside a phrase (`Sign in to the <strong>Auth Server</strong>`) breaks the match. Pick an unbroken string such as `Login</h1>`.
- **Never run these targets with `GOWORK=off` in the environment.** `go run ./cmd/oneauth-server` then can't find the package, since outside the workspace it isn't in the root module. The conformance runner drops `GOWORK` for that reason, and every server and container wait goes through `scripts/wait-for.sh`, which fails with the server's log instead of hanging.

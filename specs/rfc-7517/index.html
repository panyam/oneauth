RFC 7517 — JSON Web Key (JWK) / JSON Web Key Set (JWKS) ¶

Status: Standards Track
Published: 2015-05
L-tier / T-tier: L1 · T0 (publish) + T7 (verify)
OneAuth coverage: Implemented (keys/jwks_handler.go, keys/jwks_keystore.go)
JOSE family: JWS · JWE · JWK · JWA · JWT
See also: docs/JWT_SIGNING.md · LANDSCAPE.md

In one sentence ¶

JWK is a JSON encoding of a single cryptographic key; JWKS is the JSON array
of those keys an AS publishes for verifiers to fetch — the format behind every
/.well-known/jwks.json endpoint on the internet.

What problem does it solve? ¶

Without JWK/JWKS With JWK/JWKS
RS verifies tokens against a hardcoded public key — rotation requires a config push to every RS RS pulls the current public keys from a URL; rotation is a publish-side action
Public keys distributed as PEM (or DER, or SPKI, or PKIX) — N format dialects per implementation One JSON shape; libraries everywhere
kid (key ID) lookups need vendor-specific catalog formats Standardized — the JWKS is the catalog

JWK/JWKS turns “public key distribution” from a deploy-time problem into a
runtime problem. That’s a huge operational win.

Relatable example ¶

Open any of these in a browser; you’re looking at a JWKS:

  • Google: https://www.googleapis.com/oauth2/v3/certs
  • Microsoft: https://login.microsoftonline.com/common/discovery/v2.0/keys
  • GitHub Actions OIDC: https://token.actions.githubusercontent.com/.well-known/jwks
  • Your local OneAuth-AS: https://<as>/.well-known/jwks.json

Each one returns a JSON document like:

{
  "keys": [
    {
      "kty": "RSA",
      "use": "sig",
      "kid": "934f...",
      "alg": "RS256",
      "n": "0vx7agoebGcQ...long_base64url_modulus...",
      "e": "AQAB"
    },
    {
      "kty": "EC",
      "use": "sig",
      "kid": "ec-2025-q1",
      "alg": "ES256",
      "crv": "P-256",
      "x": "f83OJ3D2xF1Bg8vub9tLe1gHMzV76e8Tus9uPHvRVEU",
      "y": "x_FEzRu9m36HLN_tue659LNpXW6pCyStikYjKIWI5a0"
    }
  ]
}

When your RS gets a JWT with kid=934f..., it finds the matching JWK in the
set and uses (n, e) to construct the RSA public key.

Key concepts ¶

  1. kty (key type) is the discriminator. RSA, EC, OKP
    (Ed25519/Ed448), oct (symmetric). Determines which other fields appear
    (n/e for RSA, crv/x/y for EC, etc.).
  2. use and key_ops distinguish signing keys from encryption keys.
    use=sig is the OAuth norm.
  3. kid is the rotation enabler. The AS mints with one kid; publishes a
    set containing current + previous (grace-period) kids; the verifier
    matches header kid to JWK in set.
  4. Public keys only. A JWKS published at a .well-known URL must
    contain only public key material — RSA modulus and exponent (n,
    e), EC curve point (crv, x, y). Private fields (d, p, q,
    dp, dq, qi) MUST NOT be published. Symmetric keys (oct) are
    never published.
  5. RFC 7638 thumbprints give canonical fingerprints for keys (used in
    DPoP’s cnf.jkt claim — see RFC 9449).

Wire example ¶

Setup-time (T0): AS publishes JWKS.

GET /.well-known/jwks.json HTTP/1.1
Host: as.example.com

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: public, max-age=3600

{
  "keys": [
    { "kty": "RSA", "use": "sig", "kid": "rsa-2025-jun", "alg": "RS256",
      "n": "...", "e": "AQAB" },
    { "kty": "EC",  "use": "sig", "kid": "ec-2025-jun",  "alg": "ES256",
      "crv": "P-256", "x": "...", "y": "..." }
  ]
}

Verify-time (T7): RS receives a JWT, fetches JWKS, looks up kid.

JWT header: {"alg":"RS256","kid":"rsa-2025-jun","typ":"JWT"}
                                   ↓
RS reads kid → looks up entry in JWKS → reconstructs RSA public key from (n, e)
            → verifies JWS signature → trusts payload

Where it lands on the OAuth abstraction ¶

  • L1 token format. JWK is the key-encoding sibling of JWS/JWE/JWT.
  • T0 (publish) + T7 (verify). The AS publishes once at deploy; every RS
    fetches at startup and on cache-miss.
  • Critical for rotation. Without kid-driven JWKS, rotation requires a
    config push everywhere; with it, rotation is just a publish-side event.

OAuth 2.0 status ¶

Not mandated by 6749. But the JWKS pattern is the way modern 2.0 ASes
distribute verification keys for JWT-shaped access tokens and id_tokens —
universal in practice.

RFC 8414 (AS Metadata) introduced jwks_uri as a standardized metadata
field, which makes JWKS effectively required for any AS that issues
JWT-shaped tokens to consumers that don’t share private state.

OAuth 2.1 status ¶

Same as 2.0 — not formally mandated, universally deployed for asymmetric
verification.

The deliberate HS256 omission is a correctness property worth highlighting:
shared-secret algorithms have no public half, so there’s nothing legitimate
to publish. Some libraries get this wrong and accidentally leak HS256
“public” keys to clients that then treat them as verification material.

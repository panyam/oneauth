RFC 9101 — JWT-Secured Authorization Request (JAR) ¶

Status: Standards Track
Published: 2021-08
L-tier / T-tier: L6 · T1 (prepare)
OneAuth coverage: Gap (tracked under issue 338; issue 150 was consolidated into it)
See also: RFC_9126.md · LANDSCAPE.md

In one sentence ¶

JAR lets a client send its authorization request as a signed JWT —
proving integrity, authenticity, and confidentiality (if encrypted) on the
request itself, rather than relying on the browser-borne query string.

What problem does it solve? ¶

Without JAR With JAR
Authorization request parameters are tamperable in transit (browser proxy, malicious extension) Request is in a signed JWT; tampering invalidates the signature
Client identity in the request is just client_id — easily forged Signed by the client’s registered key; forgery requires the private key
Cross-organization authorization handoffs (a fintech passing a payment intent to a bank) need a way to assert “this came from us” Signed request JWT is the assertion
Some parameters (PII, payment amounts, account IDs) shouldn’t be readable in URL history JAR with encryption (JWE wrapping) hides them; pair with PAR (RFC 9126) for full URL cleanup

JAR is the integrity improvement for /authorize requests. PAR
(RFC 9126) handles the transport improvement. They’re orthogonal but
typically deployed together — JAR signs the request; PAR delivers it
back-channel.

Relatable example ¶

An open-banking third-party payment service provider (PSP) wants to
authorize a payment at a customer’s bank. The bank’s regulator requires
the request to be cryptographically attributable to the PSP — a customer-
generated forgery must be detectable.

Without JAR, the bank trusts client_id (in the URL) which any
attacker can claim. Not regulator-acceptable.

With JAR, the PSP constructs a request JWT signed by its registered
key. The bank validates: signature against the PSP’s registered public
key, iss=PSP-client-id, aud=https://bank.example, all the standard
JWT validation. Forgery now requires the PSP’s private key — out of
reach for a customer-side attacker.

GET /authorize?client_id=psp-1&request=eyJhbGciOiJSUzI1NiIs...

The signed request JWT carries the full authorization request inside
its claims. Anything in the URL outside client_id and request is
ignored by the AS.

Key concepts ¶

  1. Two delivery modes:
    • request=<signed-JWT> — request object passed as a URL parameter.
    • request_uri=<URL> — AS fetches the signed JWT from a URL
      (the client hosts it; in PAR-land the AS already has it).
  2. JWT claims (RFC 9101 §4): the request JWT carries all the
    authorization parameters as claims. Standard JWT claims (iss,
    aud, exp, iat, nbf) gate validation. Authorization claims
    (response_type, client_id, redirect_uri, scope, state,
    code_challenge, etc.) carry the request itself.
  3. iss == client_id == sub when JAR is used for request integrity.
    The signing key is the client’s registered key — same key set used
    for private_key_jwt client auth (RFC 7523).
  4. Claims outside the request JWT are ignored. Per 9101 §6.1, when
    a request JWT is present, the AS only uses claims from the JWT —
    URL parameters outside client_id and request/request_uri are
    ignored. This is the rule that prevents request-parameter smuggling.
  5. Encryption (JWE) is optional. For confidentiality, the request
    JWT can be a nested JWE-then-JWS (encrypt-then-sign or vice versa).
    Most deployments stop at JWS — encryption adds complexity for
    marginal benefit unless the URL is itself sensitive.

Decoded request JWT payload:

{
  "iss":         "psp-1",
  "aud":         "https://bank.example",
  "exp":         1717000060,
  "iat":         1717000000,
  "response_type": "code",
  "client_id":     "psp-1",
  "redirect_uri":  "https://psp.example/cb",
  "scope":         "openid payments",
  "state":         "xyz",
  "code_challenge": "E9Melh...",
  "code_challenge_method": "S256"
}

The bank validates:

  1. Signature against the PSP’s registered public key (looked up by client_id).
  2. iss == client_id, aud matches the bank’s URL, exp future, iat past.
  3. All authorization claims come from the JWT — URL client_id is the
    selector but URL redirect_uri etc. are ignored.

Delivery via request_uri (without PAR):

GET /authorize?client_id=psp-1&request_uri=https://psp.example/request-objects/abc HTTP/1.1
Host: bank.example

Bank fetches https://psp.example/request-objects/abc, validates the
JWT returned, proceeds as if request=<jwt> had been used.

Delivery via PAR + JAR (the FAPI 2.0 baseline) — see
RFC_9126.md. The signed JWT is POSTed to /par; the
returned request_uri is short and URN-shaped.

Where it lands on the OAuth abstraction ¶

  • L6 request integrity. JAR is the signature; PAR is the transport.
  • T1 (request prep). The signed request object is constructed before
    the redirect; validation happens before /authorize proceeds.
  • AS metadata fields:
    request_parameter_supported, request_uri_parameter_supported,
    request_object_signing_alg_values_supported,
    require_signed_request_object (per-client and per-deployment).

OAuth 2.0 status ¶

Published 2021 (consolidating earlier draft work going back to 2014).
Adopted by FAPI deployments and a handful of regulators. Consumer-OAuth
adoption is rare — the implementation cost outweighs the marginal benefit
unless a regulator demands integrity.

OAuth 2.1 status ¶

Not mandated by 2.1. OAuth 2.1 §4 references JAR alongside PAR; both are
optional.

FAPI 2.0 mandates JAR (signed request objects). FAPI 1.0 Advanced also
mandates it. If your trajectory is FAPI, JAR is on the critical path.

Migration path (unsigned-request → JAR) ¶

A pragmatic on-ramp:

  1. Stand up JAR validation at /authorize. Parse request /
    request_uri; verify against the client’s registered key. Reject
    if the client claims to require JAR but the request lacks it.
    Allow both forms (unsigned + JAR) initially.
  2. Add per-client policy via DCR: require_signed_request_object,
    request_object_signing_alg, request_object_encryption_alg. This
    lets you opt clients in one at a time.
  3. Advertise capabilities in AS metadata:
    request_parameter_supported: true, etc.
  4. Phase 3 — toggle deployment-wide enforcement for FAPI-track
    deployments.

The client side is straightforward — JAR libraries exist for every
language; the cost is “construct a JWT before redirect, sign with
existing private_key_jwt key.”

When NOT to use it ¶

  • Simple deployments without integrity-sensitive requests. Vanilla
    auth-code flows don’t benefit from JAR; the cost is real.
  • Public clients without registered keys. JAR requires a key the AS
    can verify against. Public clients can theoretically use dynamic keys
    (publishing in DCR) but it’s awkward; most public-client deployments
    skip JAR.
  • Deployments that already require PAR can argue JAR is redundant —
    the PAR endpoint is back-channel and client-authed, so request
    integrity is established at PAR time. FAPI 2.0 still requires JAR
    on top because defense-in-depth.

Implementation sketch. JAR composes well with existing OneAuth
machinery:

  1. Use the same JWS verifier already wired for private_key_jwt client
    auth — same allowlist, same key lookup by kid against the client’s
    registered jwks / jwks_uri.
  2. Parse incoming /authorize for request / request_uri. If present,
    validate JWT (signature, iss == client_id, aud matches issuer
    URL, exp / iat). Use JWT claims as the canonical authorization
    request; ignore URL params except client_id, request, request_uri.
  3. Add metadata fields + DCR fields.
  4. (Phase 2) Add policy enforcement: require_signed_request_object
    per-client and per-deployment.

RFC 7009 — OAuth 2.0 Token Revocation ¶

Status: Standards Track
Published: 2013-08
L-tier / T-tier: L2 · T8 (lifecycle)
OneAuth coverage: Implemented (apiauth/RevocationHandler)
See also: RFC_7662.md · RFC_9700.md · LANDSCAPE.md

In one sentence ¶

Token revocation gives clients (and servers) a way to invalidate tokens
before their natural expiry — the “Disconnect app” / “Log out everywhere”
mechanism.

What problem does it solve? ¶

Without 7009 With 7009
Refresh tokens last days/weeks/months; revoking requires custom vendor APIs One standardized endpoint; one form parameter
User logs out but their tokens stay valid until expiry — leaked-credential window Tokens dead immediately on revoke
Refresh-token rotation reuse detection needs a place to land the “burn the family” action Revocation cascades cleanly through token families
Compliance/security teams can’t audit token lifecycle endpoints — they don’t exist Standardized audit point for revocation events

7009 is the simplest L2 RFC. Two pages of normative text. The endpoint
returns 200 OK in all cases (per §2.2) — clients don’t get error feedback
about why a revocation may have failed, by design (don’t leak token
existence).

Relatable example ¶

You’re using a third-party calendar integration on your phone. You uninstall
the app. The app’s last lifecycle hook fires, and the app calls:

POST /oauth/revoke HTTP/1.1
Host: calendar-api.example.com
Authorization: Basic <client-creds>
Content-Type: application/x-www-form-urlencoded

token=long-lived-refresh-abc123&token_type_hint=refresh_token

Server returns 200 OK. The refresh token is now dead. Any access tokens
still descended from it (token family) are also revoked. Even if a backup
of the device leaks the token six months later, it’s already dead at the
server.

The “Disconnect this app” buttons in every IdP’s dashboard are 7009 calls
under the hood.

Key concepts ¶

  1. Two parameters: token and token_type_hint. The hint is
    access_token or refresh_token; AS uses it for lookup ordering but
    doesn’t require accuracy. AS searches its token store and revokes
    whichever it finds.
  2. 200 OK is the only success response. Per §2.2, ASes MUST return
    200 OK regardless of whether the token was found, already revoked,
    or never existed. This is a deliberate information-leak defense.
  3. Caller authentication required. Same as introspection — only
    authorized parties (clients revoking their own tokens, or admin
    tooling) should be able to revoke.
  4. Revoking a refresh token revokes the family. Per RFC 9700 §4.14,
    revoking a refresh token also revokes the descendant access tokens —
    this is what “log out everywhere” relies on. OneAuth’s implementation
    does this via RevokeTokenFamily.
  5. Idempotent. Revoke twice == revoke once. Safe to retry.

Wire example ¶

POST /oauth/revoke HTTP/1.1
Host: as.example.com
Content-Type: application/x-www-form-urlencoded
Authorization: Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3

token=2YotnFZFEjr1zCsicMWpAA&token_type_hint=refresh_token

HTTP/1.1 200 OK

Empty body. That’s the entire happy path. Errors (failed caller
authentication) get JSON error responses per §2.2.1 — but the token not
found / already revoked / wrong type cases all return success.

Where it lands on the OAuth abstraction ¶

  • L2 lifecycle. Revocation is the write side; introspection is the
    read side.
  • T8 (lifecycle event). Refresh / revoke / logout — the post-flow
    cleanup phase.
  • Couples tightly with RFC 9700 §4.14 (refresh token rotation with
    reuse detection). The family-revoke on reuse is exactly the operation
    this endpoint exposes for explicit invocation.

OAuth 2.0 status ¶

Part of the 2.0 ecosystem from 2013. Widely deployed; every major IdP ships
a revocation endpoint. Often advertised as part of OIDC RP-Initiated
Logout flows.

OAuth 2.1 status ¶

Not changed by 2.1. The revocation endpoint stays put with the same
semantics. 2.1’s contribution to lifecycle is requiring refresh-token
rotation with reuse detection (RFC 9700 §4.14) — and the reuse-detection
path uses revocation internally via the family-revoke action.

When NOT to use it ¶

You will always ship a revocation endpoint on a production AS. The carve-out:

  • Pure access-token-only deployments (no refresh tokens, short-lived
    access tokens, no client logout UX) can skip revocation — tokens expire
    fast enough. Rare in practice.

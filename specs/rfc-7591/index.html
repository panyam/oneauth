RFC 7591 — OAuth 2.0 Dynamic Client Registration (DCR) ¶

Status: Standards Track
Published: 2015-07
L-tier / T-tier: L3 · T0 (setup)
OneAuth coverage: Implemented (admin/DCRHandler)
See also: RFC_7592.md · LANDSCAPE.md

In one sentence ¶

DCR is the standardized way for clients to register themselves with an AS
at runtime — POST /register with a JSON metadata document, get back a
client_id (and optionally a client_secret), no human in the loop.

What problem does it solve? ¶

Without 7591 With 7591
Every new client integration requires manual provisioning — fill out a form, get sent credentials in a (hopefully encrypted) email Self-service onboarding via API call
SaaS platforms with thousands of integrating apps can’t scale developer-portal flows One AS endpoint; one JSON body
Programmatic federation (an AS auto-registering child ASes, an MCP client auto-registering against a server) requires vendor-specific APIs Standardized — works across any 7591-conformant AS
Onboarding includes ad-hoc fields per IdP Standardized client metadata schema (RFC 7591 §2)

DCR is the bedrock spec for any platform that wants to scale developer
onboarding beyond manual provisioning. It’s why modern OAuth marketplaces
(Slack app directory, Salesforce AppExchange, MCP server registries) can
function without a human approving every new client.

Relatable example ¶

You’re building a new app that integrates with Slack. Without DCR, you’d:

  1. Sign in to Slack’s developer portal
  2. Fill out a multi-page form (redirect URIs, scopes, app name, icon, …)
  3. Wait for approval
  4. Get a client_id and client_secret to paste into your config

With DCR, a developer SDK can just:

resp = requests.post(
    "https://slack.example/apps/dcr",
    json={
        "client_name": "My Integration",
        "redirect_uris": ["https://my-app.com/cb"],
        "grant_types": ["authorization_code", "refresh_token"],
        "scope": "users:read channels:read"
    }
)
creds = resp.json()
# creds: {client_id, client_secret, registration_access_token, registration_client_uri}

The whole onboarding flow becomes one HTTP POST. The MCP ecosystem in
particular is standardizing on DCR for this exact reason — connecting a
new AI agent to an MCP server should be a single API call, not a
form-filling exercise.

Key concepts ¶

  1. One endpoint: POST /register (RFC 7591 §3). Takes a JSON
    client_metadata body; returns the registered client + credentials.
  2. Standardized metadata fields (§2): redirect_uris, client_name,
    client_uri, logo_uri, scope, contacts, tos_uri, policy_uri,
    jwks_uri / jwks, token_endpoint_auth_method, grant_types,
    response_types, software_id, software_version, plus extensions
    from later RFCs (authorization_details_types for RAR,
    backchannel_logout_uri for OIDC BCL, etc.).
  3. Open vs authenticated DCR. Open DCR (§2) lets anyone register — fine
    for prototype tooling, dangerous in production. Authenticated DCR
    (§3.2) requires a registration initial access token before the
    register call succeeds. Production deployments almost always use the
    authenticated form.
  4. Returns include registration_access_token + registration_client_uri
    (§3.2.1). These tie into RFC 7592 management — the token
    lets the client later read/update/delete its own registration without
    needing initial access credentials again.
  5. Software statements (§2.3) let a third party (e.g., a software
    publisher) vouch for client metadata via a signed JWT. Allows
    “anyone can register, but only with metadata pre-blessed by Apple.”

Wire example ¶

Initial registration (open / unauthenticated):

POST /apps/dcr HTTP/1.1
Host: as.example.com
Content-Type: application/json

{
  "client_name": "Acme Calendar Integration",
  "redirect_uris": ["https://acme.example.com/oauth/cb"],
  "grant_types": ["authorization_code", "refresh_token"],
  "token_endpoint_auth_method": "client_secret_basic",
  "scope": "calendar.read calendar.write",
  "contacts": ["dev@acme.example.com"]
}

HTTP/1.1 201 Created
Content-Type: application/json
Cache-Control: no-store

{
  "client_id":                 "s6BhdRkqt3",
  "client_secret":             "cf136dc3c1fc93f31185e5885805d",
  "client_id_issued_at":       1717000000,
  "client_secret_expires_at":  0,
  "client_name":               "Acme Calendar Integration",
  "redirect_uris":             ["https://acme.example.com/oauth/cb"],
  "grant_types":               ["authorization_code", "refresh_token"],
  "token_endpoint_auth_method": "client_secret_basic",
  "scope":                     "calendar.read calendar.write",

  "registration_access_token": "reg-tok-abcdef...",                              // RFC 7592
  "registration_client_uri":   "https://as.example.com/apps/dcr/s6BhdRkqt3"      // RFC 7592
}

The client now has everything it needs to start the auth-code flow plus
the credentials to manage its own registration later.

Where it lands on the OAuth abstraction ¶

  • L3 client onboarding. DCR is the slot at T0 for “how does a new
    client get its client_id?”
  • T0 (setup). Discovery (RFC 8414) tells clients where to register;
    DCR is how they register.
  • 7591 is paired with 7592 management — issuance and
    lifecycle, one spec each.

OAuth 2.0 status ¶

Part of the 2.0 ecosystem from 2015. Most major IdPs ship DCR support — but
often gated behind admin policy. Auth0 supports it (off by default);
Keycloak supports it; Okta supports it for OIDC.

The 2.0 default is open DCR. In production this is almost always
disabled — open DCR means anyone with HTTP access to the AS can register a
client, which becomes a flood vector and a source of vanity client_ids.

OAuth 2.1 status ¶

Not directly changed by 2.1. The endpoint behavior, metadata schema, and
response shape carry through. 2.1 tightens redirect URI validation (RFC
9700 §2.1.2 / OAuth 2.1 §3.1.2) which applies at registration time — non-
HTTPS redirect URIs (other than loopback) must be rejected.

Migration path (manual provisioning → DCR) ¶

If you currently provision clients manually:

  1. Stand up the DCR endpoint behind an admin-token gate. Authenticated
    DCR with initial-access-token requirement (§3.2). This is the form
    most production IdPs ship.
  2. Migrate existing clients lazily. Don’t auto-import legacy clients
    into the DCR registry; new clients get DCR, existing ones stay where
    they are. They differ only in how they got their credentials.
  3. Wire registration_endpoint into AS metadata (RFC 8414) so
    discovery-aware client SDKs find your DCR endpoint automatically.
  4. Document the auth model — open vs initial-token vs software-statement
    gating. Each fits a different deployment posture.

When NOT to use it ¶

  • Strictly internal AS with a known, small set of clients curated by
    a platform team. The audit win of “every client provisioning is a
    ticket” can outweigh the convenience of DCR.
  • Locked-down regulated environments where every new client must go
    through a compliance review. Manual provisioning is the feature there.
  • Clients with credentials that can’t be carried in JSON — e.g.,
    hardware-key-bound clients in some FAPI deployments — need vendor
    extensions to DCR or out-of-band provisioning.

RFC 9068 — JWT Profile for OAuth 2.0 Access Tokens ¶

Status: Standards Track
Published: 2021-10
L-tier / T-tier: L1 · T5 (issue) + T7 (verify)
OneAuth coverage: Implemented
See also: RFC_7519.md · RFC_7662.md · LANDSCAPE.md

In one sentence ¶

RFC 9068 is the standard for “what does a JWT-shaped OAuth access token
look like” — it fixes the de-facto JWT shape into a normative profile with
a required claim set and a distinct typ header value (at+jwt).

What problem does it solve? ¶

Without 9068 With 9068
Every IdP ships JWT access tokens with vendor-specific claim shapes (scp vs scope, cid vs client_id, etc.) One canonical claim set; cross-vendor RS tooling becomes possible
RSes can’t distinguish “this JWT is an OAuth access token” from “this JWT is an id_token or something else” The typ:at+jwt header makes the token’s purpose self-describing
Multi-IdP RSes have to special-case each issuer’s claim names One verify path covers any 9068-conformant token
Audience handling is inconsistent Mandatory aud matched against the RS’s identifier

9068 is the bridge between “JWT is the format” (RFC 7519, generic claims)
and “and here’s how it fits OAuth 2.0 access tokens specifically.” Before
9068, every IdP’s JWT AT had a different shape. After 9068, there’s a
recognized profile.

Relatable example ¶

A modern Auth0 / Okta / Microsoft access token has these claims (roughly):

{
  "iss": "https://my-tenant.us.auth0.com/",
  "sub": "auth0|65abcd1234",
  "aud": ["https://api.example.com", "https://other-api.example.com"],
  "iat": 1717000000,
  "exp": 1717003600,
  "azp": "32555350559",
  "scope": "read:orders write:orders",
  "client_id": "32555350559",
  "jti": "abcd-1234"
}

The typ:at+jwt in the header (when the IdP sets it) is what tells your RS
“this is an access token, not an id_token.” Before 9068, you’d guess from
field presence — fragile and slow.

Key concepts ¶

  1. The typ:at+jwt header is the distinguishing mark. The original
    spec had only typ:JWT. 9068 introduces at+jwt (plus
    application/at+jwt media type) so verifiers can reject id_tokens
    masquerading as access tokens.
  2. Required claims: iss, exp, aud, sub, client_id, iat,
    jti. Note jti is REQUIRED in 9068 — not optional as in 7519. This
    enables revocation lists out of the box.
  3. Authentication info claims: auth_time, acr, amr may appear,
    carrying the how of the original authentication (helpful for
    step-up flows).
  4. scope is the standardized scope name. Some pre-9068 vendors used
    scp or scopes; 9068 settles on scope (space-separated string,
    per RFC 6749 conventions).
  5. 9068 doesn’t say “you MUST issue JWT access tokens” — it says
    “if you issue JWT access tokens, here’s the shape.” Opaque tokens +
    introspection (RFC 7662) is still an option.

Wire example ¶

A 9068-conformant access token:

HEADER  : {"typ":"at+jwt","alg":"RS256","kid":"key-2025-jun"}
PAYLOAD : {
            "iss":       "https://as.example.com",
            "exp":       1750000000,
            "aud":       ["https://api.example.com"],
            "sub":       "user-42",
            "client_id": "client-abc",
            "iat":       1749996400,
            "jti":       "fad97d2c-...",
            "scope":     "read write",

            // Optional 9068-blessed claims
            "auth_time": 1749996000,
            "acr":       "urn:ietf:params:acr:phr",
            "amr":       ["pwd", "mfa"]
          }

Verifier flow (per 9068 §4):

  1. Decode header. If typ is at+jwt (or application/at+jwt), proceed
    as access token. If typ is JWT, accept (legacy) but log. If typ
    is something else, reject.
  2. Validate JWS signature against JWKS using kid.
  3. Check iss matches expected issuer.
  4. Check aud includes this RS’s identifier.
  5. Check exp is in the future.
  6. (Optional) Check jti against revocation list.
  7. Authorize based on scope + (if RAR) authorization_details.

Where it lands on the OAuth abstraction ¶

  • L1 token format. 9068 is JWT (7519) + OAuth access-token specifics.
  • T5 (issue) + T7 (verify). AS mints in 9068 shape; RS validates.
  • 9068 is one half of the L1 decision tree at T7:
    • JWT-shaped (9068) → local verify
    • Opaque → introspect (7662)

OAuth 2.0 status ¶

Published 2021 — years after 2.0. Not part of 6749. Not mandatory for 2.0
conformance. But: nearly every modern 2.0 deployment that ships JWT access
tokens uses (or could use) the 9068 shape because:

  • Cross-vendor tooling expects it
  • The typ:at+jwt header eliminates a class of token-confusion bugs
  • Standard claim names mean libraries Just Work without per-vendor configs

If you’re issuing JWT access tokens against bare 2.0 today, follow 9068.
Backward compatibility cost is tiny (you’re adding a typ header that old
consumers ignore).

OAuth 2.1 status ¶

Not mandated by 2.1 either. Same status as 2.0: “follow this if you ship
JWT access tokens; opaque tokens + introspection (7662) remain a valid
alternative.”

OAuth 2.1’s stance on access-token format is deliberately neutral. The
spec wants to leave room for sender-constrained tokens (DPoP, mTLS) and
introspection-based deployments equally.

Migration path (pre-9068 JWT → 9068-conformant) ¶

If your AS already issues JWT access tokens but predates 9068:

  1. Add the typ:at+jwt header to new tokens. Old verifiers that ignore
    typ continue to work; new verifiers can distinguish.
  2. Ensure required claims are present: iss, exp, aud, sub,
    client_id, iat, jti. The newcomer is usually jti — wire it
    to a UUID or other unique generator.
  3. Migrate vendor-specific claim names to the standard ones (scp →
    scope, cid → client_id, etc.). Either:
    • Soft migration: emit both old and new names for a window; deprecate
      old later
    • Hard migration: cut over once all RSes can parse the new names
  4. Audit aud: 9068 makes aud required and expects the RS to verify
    itself in the list. Some pre-9068 ASes shipped tokens without aud or
    with a placeholder; fix.
  5. Validate the typ at the RS side — reject id_tokens (typ=JWT with
    id-specific claims) presented to access-token endpoints.

This is mostly additive — most pre-9068 implementations only need the
typ header and jti to become 9068-conformant.

When NOT to use it ¶

If you’ve made a deliberate choice for opaque tokens (centralized revocation,
no in-line credential exposure to clients, regulatory requirements), 9068
doesn’t apply — you’re on the RFC 7662 introspection path instead.

Otherwise: if you ship JWT access tokens, ship them per 9068. The cost is
zero and the cross-vendor compatibility win is large.
